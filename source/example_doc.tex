\section{An example notebook}\label{an-example-notebook}

If you want to see an example of documented code, have a look at
\href{https://github.com/ndombrowski/cli_workshop/tree/main/example_doc}{a
notebook} that I wrote for the analysis we do in this tutorial. You can
think of it as a cleaned-up version of the \texttt{notes.md} notebook
that you kept during the workshop.

The link above shows you:

\begin{itemize}
\tightlist
\item
  How you can use GitHub to make your code available to others
\item
  What a code notebook can look like. The notebook is a Quarto file,
  which you find
  \href{https://github.com/ndombrowski/cli_workshop/blob/main/example_doc/example_notebook.qmd}{here}.
  To make it easier to read for collaborators, I also turned it into an
  \href{https://ndombrowski.github.io/cli_workshop/example_doc/example_notebook.html}{HTML
  report}.
\end{itemize}

The example uses the same data as this tutorial, so the code might only
make sense after you have finished the tutorial. Feel free to come back
to this page after you have written some code yourself.

This is just one example to get you started. Your own notebook might
look different, depending on your needs.

Below, you find some hints on what to put into the different sections of
the notebook.

\subsection{YAML headers}\label{yaml-headers}

\includegraphics[width=7.84375in,height=\textheight,keepaspectratio]{../img/yaml_header.png}

The \textbf{YAML header} is the part between the two \texttt{-\/-\/-}
lines at the very top of the file. It contains settings for the whole
document, such as the title, the author and the output format. In my
example, \texttt{eval:\ false} tells Quarto to only show the code, not
to run it.

\subsection{Settings (change these before you run the
workflow)}\label{settings-change-these-before-you-run-the-workflow}

\includegraphics[width=5.71875in,height=\textheight,keepaspectratio]{../img/general_setup.png}

In one of the first sections of my notebooks, I collect everything that
someone who wants to use my workflow has to change. I write the code
below this section in a way that it does not need to be changed. This
way, another person can run my code as it is, and only needs to edit
this first section. Typical things to add here are:

\begin{itemize}
\tightlist
\item
  Where the analysis starts: the location of the working directory or
  project folder
\item
  Custom paths, for example to databases that need to be downloaded from
  the web
\item
  Custom variables. In the example above, I store the location of my
  project folder in a variable called \texttt{wdir}. I use
  \texttt{\$HOME} in it instead of typing out my home directory, so the
  path works for anyone with the same folder structure on Crunchomics. I
  also store the link to the data in a variable called
  \texttt{download\_link}, and use this variable further down to
  download the data. If the link to the data ever changes, another
  person only needs to change it in this one place, and the code below
  stays the same. When you write code, try to think ahead: keep the
  number of places that need to be changed as small as possible.
\end{itemize}

I tend NOT to write down how I log in to the HPC with \texttt{ssh} and
copy data with \texttt{scp}. That way, my user name and login
information stay private.

\subsection{Looking at the data (sanity
checks)}\label{looking-at-the-data-sanity-checks}

\includegraphics[width=5.84375in,height=\textheight,keepaspectratio]{../img/sanity_check.png}

When I start working with new data, I add as many sanity checks as
possible, to make sure that my data looks good. That way, I notice
problems early, before they cause trouble further down the line. At the
same time, I get to know my data better: how many samples and how much
data I am working with.

I also add sanity checks whenever I change my data. For example, when I
merge several files into one large file, I might count the lines of the
individual files and of the combined file, to make sure that I used my
wildcards correctly.

Remember: the computer is only as smart as the person using it, and it
runs your commands blindly. So the computer can do unexpected things,
and you need to check for that.

\subsection{Using Markdown to make
notes}\label{using-markdown-to-make-notes}

\includegraphics[width=5.65625in,height=\textheight,keepaspectratio]{../img/comments_in_code.png}

In the example above, I use Markdown not only to document my code, but
also to add notes wherever I need them. Here, I wrote down what the
results of seqkit stats and the fastp HTML reports actually told me.

This kind of documentation can be useful for:

\begin{itemize}
\tightlist
\item
  Justifying decisions further down the line. In this example, I might
  decide on how to clean the sequencing data. For example, when I looked
  at the FastP HTML report I noticed a dip in quality at the end of the
  sequence reads. Based on that I normally would make a decision to
  adjust re-run FastP and enable trimming of the reads.
\item
  Future you. If you read the report a month, or a year, later you have
  the key information in your report and don't have to open any files or
  tables that are located elsewhere
\end{itemize}

\subsection{Documenting external
scripts}\label{documenting-external-scripts}

\includegraphics[width=5.82292in,height=\textheight,keepaspectratio]{../img/external_scripts.png}

This part makes more sense after you have worked through the HPC part of
the tutorial. Here, my notebook only says that I submitted a script to
the HPC with \texttt{sbatch}. It does not say how I ran seqkit: that
code is ``hidden'' inside the \texttt{seqkit.sh} script. So someone who
reads only the notebook does not see the code right away. You can deal
with this in two ways:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Instead of the \texttt{sbatch} command, write the actual command that
  ran on the compute node into your notebook.
\item
  Keep the scripts next to your notebook, and when you publish your code
  with a paper, publish the whole \texttt{scripts} folder too, for
  example on
  \href{https://github.com/ndombrowski/cli_workshop/tree/main/example_doc}{GitHub}
  or \href{https://zenodo.org/records/3839790}{Zenodo}. This is why you
  copied the job scripts to your own computer at the end of day 2.
\end{enumerate}

I prefer option 2, because I like to record the code in my notebooks
exactly as I ran it. But you can do it differently, as long as all the
code you ran is written down and available to others once you publish
your data.

\section{Going further}\label{going-further}

\subsection{\texorpdfstring{From \texttt{notes.md} to a Quarto
document}{From notes.md to a Quarto document}}\label{from-notes.md-to-a-quarto-document}

Your \texttt{notes.md} and my example notebook are written in the same
way: Markdown text with code blocks. The difference is that the example
notebook is a \textbf{Quarto} document (it ends in \texttt{.qmd}).
Quarto turns such a file into a web page (HTML), a PDF or a Word file,
with a table of contents and colored code. That makes it easier to share
your notebook with others, for example with your supervisor or together
with a paper.

If you want to try this in RStudio (recent versions of RStudio come with
Quarto):

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Go to \textbf{File}, then \textbf{New File}, then \textbf{Quarto
  Document}
\item
  Copy the content of your \texttt{notes.md} into the new file, below
  the YAML header at the top (see ``YAML headers'' above)
\item
  Save the file and click \textbf{Render}
\end{enumerate}

Code blocks that you wrote as
\texttt{\textasciigrave{}\textasciigrave{}\textasciigrave{}bash}, like
in your notes, are only shown on the page, not run. The
\href{https://quarto.org/docs/get-started/hello/rstudio.html}{Quarto
tutorial for RStudio} explains the next steps.

\subsection{Further reading}\label{further-reading}

\begin{itemize}
\tightlist
\item
  \href{https://assets.britishecologicalsociety.org/2017/12/guide-to-reproducible-code.pdf}{A
  Guide to Reproducible Code in Ecology and Evolution} from the British
  Ecological Society explains how to organize project folders and how to
  write clear code that others can rerun. The examples are mostly in R,
  but the advice applies to bash and other languages as well.
\item
  \href{https://quarto.org/docs/authoring/markdown-basics.html}{Markdown
  Basics} on the Quarto website lists everything else you can do with
  Markdown, for example lists, links, bold text, images and tables.
\end{itemize}
