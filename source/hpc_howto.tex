\chapter{Using an HPC}\label{using-an-hpc}

Now that you are more familiar with the command line, we will learn how
to work on the UvA Crunchomics HPC. On this page, you will:

\begin{itemize}
\tightlist
\item
  Connect to Crunchomics and prepare your account
\item
  Transfer the sequencing data from your own computer to Crunchomics
\item
  Run your first analyses on the compute nodes with SLURM:

  \begin{itemize}
  \tightlist
  \item
    \texttt{srun} for short, interactive analyses
  \item
    \texttt{sbatch} for longer running, more resource intensive analyses
  \end{itemize}
\item
  Install your own software with conda
\end{itemize}

For people following this tutorial outside of UvA:

\begin{itemize}
\tightlist
\item
  If you have access to an HPC that uses SLURM, you can still follow the
  tutorial
\item
  If you do not have access to an HPC but are interested in how to
  install and run software that can be used to analyse sequencing data,
  you still might want to check out the steps below. The dataset is very
  small and all analyses can be run on a desktop computer
\end{itemize}

\section{Connecting to the HPC}\label{connecting-to-the-hpc}

\subsection{\texorpdfstring{\texttt{ssh}: Connecting to a
server}{ssh: Connecting to a server}}\label{ssh-connecting-to-a-server}

\textbf{SSH} (Secure Shell) is a network protocol that allows you to
securely connect to a remote computer, such as the Crunchomics HPC. The
general command looks like this:

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{ssh}\NormalTok{ username@server}
\end{Highlighting}
\end{Shaded}

Here:

\begin{itemize}
\tightlist
\item
  \texttt{username} is your account name on the HPC. For Crunchomics,
  this is your UvAnetID
\item
  \texttt{server} is the address of the HPC you want to connect to. For
  Crunchomics, this is \texttt{omics-h0.science.uva.nl}
\end{itemize}

To log in to Crunchomics, use the following command and enter your UvA
password when you are asked for it. Remember that nothing appears on the
screen while you type your password:

\begin{Shaded}
\begin{Highlighting}[]
\CommentTok{\# Log in to Crunchomics (replace uvanetid with your own UvAnetID)}
\FunctionTok{ssh}\NormalTok{ uvanetid@omics{-}h0.science.uva.nl}
\end{Highlighting}
\end{Shaded}

You did the same during the \href{installation.qmd}{Before you start}
checks. After logging in, the prompt changes: it now shows your UvAnetID
and \texttt{omics-h0}. Every command you type now runs on Crunchomics,
not on your own computer.

\begin{tcolorbox}[enhanced jigsaw, left=2mm, colframe=quarto-callout-important-color-frame, toprule=.15mm, arc=.35mm, colback=white, colbacktitle=quarto-callout-important-color!10!white, opacitybacktitle=0.6, titlerule=0mm, opacityback=0, bottomrule=.15mm, bottomtitle=1mm, toptitle=1mm, title=\textcolor{quarto-callout-important-color}{\faExclamation}\hspace{0.5em}{Important}, leftrule=.75mm, breakable, rightrule=.15mm, coltitle=black]

\textbf{Important tips for connecting:}

\begin{itemize}
\tightlist
\item
  If you want to log in to Crunchomics while working from UvA, use the
  eduroam network, not the open Amsterdam Science Park network
\item
  If you are connecting from outside UvA, you must be connected to the
  VPN. Contact ICT if you have not set it up or encounter issues
\item
  Always double-check your username and the server address to avoid
  login errors
\end{itemize}

\end{tcolorbox}

\begin{tcolorbox}[enhanced jigsaw, left=2mm, colframe=quarto-callout-tip-color-frame, toprule=.15mm, arc=.35mm, colback=white, colbacktitle=quarto-callout-tip-color!10!white, opacitybacktitle=0.6, titlerule=0mm, opacityback=0, bottomrule=.15mm, bottomtitle=1mm, toptitle=1mm, title=\textcolor{quarto-callout-tip-color}{\faLightbulb}\hspace{0.5em}{Tip: Viewing graphical output with ssh -X}, leftrule=.75mm, breakable, rightrule=.15mm, coltitle=black]

Some programs on the HPC can open a window, for example to show a plot
or a PDF. To see such windows on your own computer, log in with the
\texttt{-X} option:

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{ssh} \AttributeTok{{-}X}\NormalTok{ uvanetid@omics{-}h0.science.uva.nl}
\end{Highlighting}
\end{Shaded}

\texttt{-X} enables what is called \textbf{X11 forwarding}: the HPC
sends the graphical output to your computer. In this tutorial we don't
need this, because we copy the results to our own computer instead.

\end{tcolorbox}

\begin{tcolorbox}[enhanced jigsaw, left=2mm, colframe=quarto-callout-tip-color-frame, toprule=.15mm, arc=.35mm, colback=white, colbacktitle=quarto-callout-tip-color!10!white, opacitybacktitle=0.6, titlerule=0mm, opacityback=0, bottomrule=.15mm, bottomtitle=1mm, toptitle=1mm, title=\textcolor{quarto-callout-tip-color}{\faLightbulb}\hspace{0.5em}{Tip: Warning about a changed host key}, leftrule=.75mm, breakable, rightrule=.15mm, coltitle=black]

The first time you connect, your computer stores a ``fingerprint'' of
Crunchomics, the so-called host key. After maintenance of Crunchomics,
this key can change. Then \texttt{ssh} refuses to connect and shows a
warning like \texttt{REMOTE\ HOST\ IDENTIFICATION\ HAS\ CHANGED!}.

If you know that Crunchomics had maintenance, you can remove the old key
from your computer with the command below. Run it on your own computer,
not on the HPC. Then log in again and type \texttt{yes} when you are
asked whether you want to continue connecting.

\begin{Shaded}
\begin{Highlighting}[]
\CommentTok{\# Remove the stored host key for Crunchomics from your own computer}
\FunctionTok{ssh{-}keygen} \AttributeTok{{-}R} \StringTok{"omics{-}h0.science.uva.nl"}
\end{Highlighting}
\end{Shaded}

If you are unsure why the key changed, ask before you remove it.

\end{tcolorbox}

\subsection{Crunchomics: Preparing your
account}\label{crunchomics-preparing-your-account}

If this is your \textbf{first time using Crunchomics}, you need to run a
small bash script to set up your account. Ignore this section if you
have done this before. The script:

\begin{itemize}
\tightlist
\item
  Adds \texttt{/zfs/omics/software/bin} to your PATH. The \textbf{PATH}
  is the list of folders in which bash looks for programs. With this
  change, bash can find the software that is already installed on
  Crunchomics
\item
  Sets up a Python 3 environment with some useful Python packages
\item
  Creates a link called \texttt{personal} in your home directory. This
  link leads to your personal directory, which has 500 GB of space. Your
  home directory itself only has 25 GB
\end{itemize}

To set up your account, run the following commands:

\begin{Shaded}
\begin{Highlighting}[]
\CommentTok{\# First, orient yourself}
\BuiltInTok{pwd}
\FunctionTok{ls} \AttributeTok{{-}lh}

\CommentTok{\# Run the Crunchomics installation script}
\ExtensionTok{/zfs/omics/software/script/omics\_install\_script}

\CommentTok{\# Check what changed}
\CommentTok{\# You should now see the personal folder inside your home directory}
\FunctionTok{ls} \AttributeTok{{-}lh}
\end{Highlighting}
\end{Shaded}

\subsection{Preparing your working
directory}\label{preparing-your-working-directory}

Next, let's make a project folder for our analyses. Always make project
folders inside your personal directory, since it has much more space
than your home directory. We give the folder the same name as on our own
computer, \texttt{data\_analysis}:

\begin{Shaded}
\begin{Highlighting}[]
\CommentTok{\# Go into the personal folder}
\BuiltInTok{cd}\NormalTok{ personal}

\CommentTok{\# Make a new project folder and go into it}
\FunctionTok{mkdir}\NormalTok{ data\_analysis}
\BuiltInTok{cd}\NormalTok{ data\_analysis}

\CommentTok{\# Check that you are in the right folder}
\BuiltInTok{pwd}
\end{Highlighting}
\end{Shaded}

You now have a clean workspace for all the analyses that you will run on
Crunchomics. As on your own computer, it is good practice to keep your
raw data, results and scripts in separate folders.

\subsection{\texorpdfstring{\texttt{scp}: Transferring data to and from
a
server}{scp: Transferring data to and from a server}}\label{scp-transferring-data-to-and-from-a-server}

Next, we want to transfer the \texttt{data} folder with our sequencing
data from our own computer to the new project folder on Crunchomics. We
do this with \texttt{scp} (Secure Copy Protocol), which securely copies
files and folders between your computer and a remote server.

The basic syntax is:

\begin{itemize}
\tightlist
\item
  \texttt{scp\ {[}options{]}\ SOURCE\ DESTINATION}
\item
  A location on a server is written as
  \texttt{username@server:path\_on\_the\_server}
\end{itemize}

When transferring data, you must \textbf{run \texttt{scp} in a terminal
on your own computer}, not in a terminal that is logged in to the HPC.
To keep yourself organized, it is useful to have two terminals open: one
on your own computer and one on Crunchomics. In MobaXterm, you can open
a second terminal in a new tab:

To copy the entire \texttt{data} folder into your Crunchomics project
folder, use:

\begin{Shaded}
\begin{Highlighting}[]
\CommentTok{\# Run this in the terminal on your OWN computer (not on the HPC),}
\CommentTok{\# from inside your local data\_analysis folder (where the data folder is)}
\CommentTok{\# Replace both instances of \textquotesingle{}username\textquotesingle{} with your UvAnetID}
\FunctionTok{scp} \AttributeTok{{-}r}\NormalTok{ data username@omics{-}h0.science.uva.nl:/home/username/personal/data\_analysis}
\end{Highlighting}
\end{Shaded}

Here:

\begin{itemize}
\tightlist
\item
  \texttt{-r} copies a folder together with everything inside it
  (\textbf{recursive}). Without \texttt{-r}, \texttt{scp} only copies
  single files
\item
  \texttt{data} is the source: the folder on your own computer
\item
  \texttt{username@omics-h0.science.uva.nl:/home/username/personal/data\_analysis}
  is the destination: your project folder on Crunchomics
\end{itemize}

Now switch to the terminal that is logged in to Crunchomics and check
that the files arrived:

\begin{Shaded}
\begin{Highlighting}[]
\CommentTok{\# Run this on Crunchomics, inside the data\_analysis folder}
\FunctionTok{ls} \AttributeTok{{-}l}\NormalTok{ data/seq\_project/}\PreprocessorTok{*}\NormalTok{/}\PreprocessorTok{*}\NormalTok{fastq.gz}

\CommentTok{\# We expect 8 files (4 samples, R1 and R2 each)}
\FunctionTok{ls}\NormalTok{ data/seq\_project/}\PreprocessorTok{*}\NormalTok{/}\PreprocessorTok{*}\NormalTok{fastq.gz }\KeywordTok{|} \FunctionTok{wc} \AttributeTok{{-}l}
\end{Highlighting}
\end{Shaded}

\begin{tcolorbox}[enhanced jigsaw, left=2mm, colframe=quarto-callout-tip-color-frame, toprule=.15mm, arc=.35mm, colback=white, colbacktitle=quarto-callout-tip-color!10!white, opacitybacktitle=0.6, titlerule=0mm, opacityback=0, bottomrule=.15mm, bottomtitle=1mm, toptitle=1mm, title=\textcolor{quarto-callout-tip-color}{\faLightbulb}\hspace{0.5em}{Tip: Moving data from the HPC to your own computer}, leftrule=.75mm, breakable, rightrule=.15mm, coltitle=black]

You can also copy results from the HPC to your own computer. For this,
you switch source and destination. For example, to copy a single
sequencing file from Crunchomics:

\begin{itemize}
\tightlist
\item
  We do not need \texttt{-r}, since we only copy a single file
\item
  We again run this command in a terminal on our own computer, not on
  the HPC
\item
  The \texttt{.} at the end means ``copy into the folder I am in right
  now'' on your own computer. If you want to copy the file elsewhere,
  replace \texttt{.} with a path
\end{itemize}

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{scp}\NormalTok{ username@omics{-}h0.science.uva.nl:/home/username/personal/data\_analysis/data/seq\_project/barcode001\_User1\_ITS\_1\_L001/Sample{-}DUMMY1\_R1.fastq.gz .}
\end{Highlighting}
\end{Shaded}

\end{tcolorbox}

\begin{tcolorbox}[enhanced jigsaw, left=2mm, colframe=quarto-callout-tip-color-frame, toprule=.15mm, arc=.35mm, colback=white, colbacktitle=quarto-callout-tip-color!10!white, opacitybacktitle=0.6, titlerule=0mm, opacityback=0, bottomrule=.15mm, bottomtitle=1mm, toptitle=1mm, title=\textcolor{quarto-callout-tip-color}{\faLightbulb}\hspace{0.5em}{Tip: Moving files with wildcards}, leftrule=.75mm, breakable, rightrule=.15mm, coltitle=black]

We can also copy several files at once with a wildcard. Then
\texttt{scp} copies only the files, not the folders they are in.

\begin{Shaded}
\begin{Highlighting}[]
\CommentTok{\# On Crunchomics: make a folder to copy the data into}
\FunctionTok{mkdir}\NormalTok{ transfer\_test}

\CommentTok{\# On your own computer: copy all fastq.gz files to the new folder on Crunchomics}
\FunctionTok{scp}\NormalTok{ data/seq\_project/barcode00}\PreprocessorTok{*}\NormalTok{/}\PreprocessorTok{*}\NormalTok{fastq.gz username@omics{-}h0.science.uva.nl:/home/username/personal/data\_analysis/transfer\_test}

\CommentTok{\# On Crunchomics: view the data}
\CommentTok{\# See how the folder structure is different compared to our first example?}
\FunctionTok{ls} \AttributeTok{{-}l}\NormalTok{ transfer\_test/}\PreprocessorTok{*}
\end{Highlighting}
\end{Shaded}

\textbf{Notice for Mac users}:

For Mac users who work with the zsh shell, the command above might not
work, and you might get an error like ``file not found'', ``no matches
found'' or something similar. zsh handles wildcards slightly differently
than bash. If you see this error and you are sure that the files exist,
try this version of the command:

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{\textbackslash{}scp}\NormalTok{ data/seq\_project/barcode00}\PreprocessorTok{*}\NormalTok{/}\PreprocessorTok{*}\NormalTok{fastq.gz username@omics{-}h0.science.uva.nl:/home/username/personal/data\_analysis/transfer\_test}
\end{Highlighting}
\end{Shaded}

If that does not work, these are some other things to try (different zsh
setups might need slightly different solutions):

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{noglob}\NormalTok{ scp data/seq\_project/barcode00}\PreprocessorTok{*}\NormalTok{/}\PreprocessorTok{*}\NormalTok{fastq.gz username@omics{-}h0.science.uva.nl:/home/username/personal/data\_analysis/transfer\_test}

\FunctionTok{scp} \StringTok{\textquotesingle{}data/seq\_project/barcode00*/*fastq.gz\textquotesingle{}}\NormalTok{ username@omics{-}h0.science.uva.nl:/home/username/personal/data\_analysis/transfer\_test}
\end{Highlighting}

\section{Submitting jobs with SLURM}\label{submitting-jobs-with-slurm}

\subsection{Login node and compute
nodes}\label{login-node-and-compute-nodes}

In the HPC introduction, you learned that an HPC has two main parts:

\begin{itemize}
\tightlist
\item
  The \textbf{login node}: where you log in and do light work, such as
  moving files, editing scripts or preparing jobs
\item
  The \textbf{compute nodes}: where the actual analyses run. These nodes
  have more CPUs and memory
\end{itemize}

We do not run big analyses on the login node. Instead, we send them to
the compute nodes as \textbf{jobs}. A job is a task that you ask the HPC
to run, together with the resources it needs. The jobs are managed by
\textbf{SLURM}, a workload manager that decides \emph{when},
\emph{where} and \emph{how} your jobs run based on the available
resources.

\subsection{\texorpdfstring{\texttt{sinfo}: Get information about the
cluster}{sinfo: Get information about the cluster}}\label{sinfo-get-information-about-the-cluster}

When you start on a new HPC, it is useful to know which compute nodes
exist and how busy they are. This helps you to choose how many resources
to request, so that your job runs efficiently but also starts in time.

To get a list of the compute nodes, type:

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{sinfo}
\end{Highlighting}
\end{Shaded}

We will see something like this:

\includegraphics[width=0.6\linewidth,height=\textheight,keepaspectratio]{../img/sinfo.png}\hfill

Here, the different columns are:

\begin{itemize}
\tightlist
\item
  PARTITION: the queues that are available. Crunchomics has only a few
  partitions, and you do not need to choose one. Other systems use
  partitions to group nodes with different hardware or a different
  maximum run time
\item
  STATE: tells you whether a node is busy or not:

  \begin{itemize}
  \tightlist
  \item
    mix: some of the resources are in use
  \item
    idle: the node is free
  \item
    drain: unavailable, because the system administrator asked for it
  \item
    alloc: all resources are in use
  \item
    down: unavailable
  \end{itemize}
\item
  NODES: the number of nodes in each state
\item
  NODELIST: the names of the compute nodes
\end{itemize}

queue}{squeue: View the jobs in the queue}}\label{squeue-view-the-jobs-in-the-queue}

in the queue:

\begin{Shaded}
\begin{Highlighting}[]

\end{Highlighting}
\end{Shaded}

This shows all jobs on the system and might look something like this:

\includegraphics[width=0.5\linewidth,height=\textheight,keepaspectratio]{../img/squeue.png}\hfill

Some useful columns to know:

\begin{itemize}
\tightlist
\item
  JOBID: a unique number for each job. You can use it to check on or

\item

Once you have submitted a job, it appears in this list as well. To see

\subsection{\texorpdfstring{\texttt{srun}: Submitting a job
interactively}{srun: Submitting a job interactively}}\label{srun-submitting-a-job-interactively}

Now let's run our first job on a compute node. There are two main ways
to submit jobs: \texttt{srun} and \texttt{sbatch}. We start with
\texttt{srun}, which you typically use when:

\begin{itemize}
\tightlist
\item
  You want to run tasks \textbf{interactively} and see the output
  directly on your screen
\item
  You are \textbf{testing or debugging} your commands before writing a
  job script
\item
  You have \textbf{short jobs} (usually less than a few hours)
\end{itemize}

Let's start with a very simple example to see how \texttt{srun} works:

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{srun} \AttributeTok{{-}{-}cpus{-}per{-}task}\OperatorTok{=}\NormalTok{1 }\AttributeTok{{-}{-}mem}\OperatorTok{=}\NormalTok{1G }\AttributeTok{{-}{-}time}\OperatorTok{=}\NormalTok{00:10:00 echo }\StringTok{"Hello world"}
\end{Highlighting}
\end{Shaded}

Here's what each part means:

\begin{itemize}
\tightlist
\item
  \texttt{srun}: tells SLURM that you want to run something on a compute
  node, with the resources that follow
\item
  \texttt{-\/-cpus-per-task=1}: request 1 CPU
\item
  \texttt{-\/-mem=1G}: request 1 GB of memory
\item
  \texttt{-\/-time=00:10:00}: set a maximum run time of 10 minutes
  (hours:minutes:seconds). If the job takes longer, SLURM stops it
\item
  \texttt{echo\ "Hello\ world"}: the actual command to run
\end{itemize}

So everything between \texttt{srun} and the actual command tells SLURM
which resources your job needs on the compute node. The job runs so fast
that you won't see it in \texttt{squeue}. But congratulations, you just
communicated with a compute node for the first time.

\begin{tcolorbox}[enhanced jigsaw, left=2mm, colframe=quarto-callout-important-color-frame, toprule=.15mm, arc=.35mm, colback=white, colbacktitle=quarto-callout-important-color!10!white, opacitybacktitle=0.6, titlerule=0mm, opacityback=0, bottomrule=.15mm, bottomtitle=1mm, toptitle=1mm, title=\textcolor{quarto-callout-important-color}{\faExclamation}\hspace{0.5em}{Important}, leftrule=.75mm, breakable, rightrule=.15mm, coltitle=black]

Jobs started with \texttt{srun} stop if you lose the connection to the
HPC, for example when you close your laptop. For longer jobs, use
\texttt{sbatch} (see below).

\end{tcolorbox}

\begin{tcolorbox}[enhanced jigsaw, left=2mm, colframe=quarto-callout-tip-color-frame, toprule=.15mm, arc=.35mm, colback=white, colbacktitle=quarto-callout-tip-color!10!white, opacitybacktitle=0.6, titlerule=0mm, opacityback=0, bottomrule=.15mm, bottomtitle=1mm, toptitle=1mm, title=\textcolor{quarto-callout-tip-color}{\faLightbulb}\hspace{0.5em}{Tip: Other srun options you might see}, leftrule=.75mm, breakable, rightrule=.15mm, coltitle=black]

In examples online, you will often see two more options:

\begin{itemize}
\tightlist
\item
  \texttt{-\/-nodes=1}: the number of nodes (i.e.~separate computers)
  your job runs on. This does not reserve the whole node for you, jobs
  of other people can still run on the same node. The CPUs you request
  with \texttt{-\/-cpus-per-task} always come from a single node, so for
  the jobs in this tutorial you can leave this option out. If you ever
  really need a whole node for yourself, the option for that is
  \texttt{-\/-exclusive}, but on a shared system like Crunchomics you
  rarely want this.
\item
  \texttt{-\/-ntasks=1}: the number of tasks to run. The default is 1,
  which is what we need in this tutorial
\end{itemize}

\end{tcolorbox}

Next, let's use \texttt{srun} for something more useful.
\href{https://www.bioinformatics.babraham.ac.uk/projects/fastqc/}{FastQC}
is a quality control tool for sequencing data that is already installed

Whenever you use a tool for the first time, check its help page

Sometimes you want to try out several commands after each other on a
compute node, for example to test a new tool. Instead of putting
\texttt{srun} in front of every command, you can open an
\textbf{interactive session}: a shell that runs on a compute node.

\begin{Shaded}
\begin{Highlighting}[]
\CommentTok{\# Open an interactive bash shell on a compute node for at most 1 hour}
\ExtensionTok{srun} \AttributeTok{{-}{-}cpus{-}per{-}task}\OperatorTok{=}\NormalTok{1 }\AttributeTok{{-}{-}mem}\OperatorTok{=}\NormalTok{5G }\AttributeTok{{-}{-}time}\OperatorTok{=}\NormalTok{01:00:00 }\AttributeTok{{-}{-}pty}\NormalTok{ bash }\AttributeTok{{-}i}
\end{Highlighting}
\end{Shaded}

Here:

\begin{itemize}
\tightlist
\item
  \texttt{-\/-pty\ bash\ -i} starts an interactive bash shell on the
  compute node, instead of running a single command
\end{itemize}

Your prompt changes: it now shows the name of the compute node instead
of \texttt{omics-h0}. You can check where you are with the command
\texttt{hostname}, which prints the name of the computer you are working
on. Every command you type now runs on the compute node, with the
resources you requested.

When you are done, leave the compute node and go back to the login node:

\begin{Shaded}
\begin{Highlighting}[]
\BuiltInTok{exit}
\end{Highlighting}
\end{Shaded}

as the session is open, the CPUs and memory you requested stay reserved
for you, even if you don't use them, and other people have to wait for
them.

\subsection{\texorpdfstring{\texttt{sbatch}: Submitting a long-running
job}{sbatch: Submitting a long-running job}}\label{sbatch-submitting-a-long-running-job}

While \texttt{srun} is great for quick, interactive runs, most analyses
on an HPC are submitted with \textbf{\texttt{sbatch}}. With
\texttt{sbatch}, you write your commands into a \textbf{job script}, a
text file with all the commands and the resources your job needs. SLURM
then runs the script in the background, even after you log out.

Use \texttt{sbatch} when:

\begin{itemize}
\tightlist
\item
  You have \textbf{long or resource-intensive} analyses
\item
  You want jobs to run \textbf{unattended}, without your direct
  supervision
\item
  You want to \textbf{run several jobs} after each other or at the same
  time
\end{itemize}

\subsubsection{Step 1: Create folders for scripts and
logs}\label{step-1-create-folders-for-scripts-and-logs}

We keep our project tidy by making separate folders for our job scripts
and for the log files that SLURM writes:

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{mkdir} \AttributeTok{{-}p}\NormalTok{ scripts logs}

\CommentTok{\# Check that the folders are there}
\FunctionTok{ls} \AttributeTok{{-}l}
\end{Highlighting}
\end{Shaded}

\subsubsection{Step 2: Write a job
script}\label{step-2-write-a-job-script}

We run FastQC again, but this time with \texttt{sbatch} instead of
\texttt{srun}, so that you can directly compare the two.

Use \texttt{nano} to create a script file:

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{nano}\NormalTok{ scripts/run\_fastqc.sh}
\end{Highlighting}
\end{Shaded}

Then add the following content:

\begin{Shaded}
\begin{Highlighting}[]
\CommentTok{\#!/bin/bash}
\CommentTok{\#SBATCH {-}{-}job{-}name=fastqc}
\CommentTok{\#SBATCH {-}{-}output=logs/fastqc\_\%j.out}
\CommentTok{\#SBATCH {-}{-}error=logs/fastqc\_\%j.err}
\CommentTok{\#SBATCH {-}{-}cpus{-}per{-}task=1}
\CommentTok{\#SBATCH {-}{-}mem=5G}
\CommentTok{\#SBATCH {-}{-}time=01:00:00}

\BuiltInTok{echo} \StringTok{"FastQC job started on:"}
\FunctionTok{date}

\ExtensionTok{fastqc}\NormalTok{ data/seq\_project/}\PreprocessorTok{*}\NormalTok{/}\PreprocessorTok{*}\NormalTok{gz }\AttributeTok{{-}o}\NormalTok{ results/fastqc }\AttributeTok{{-}{-}threads}\NormalTok{ 1}

\BuiltInTok{echo} \StringTok{"FastQC job finished on:"}
\FunctionTok{date}
\end{Highlighting}
\end{Shaded}

Save and exit:

\begin{itemize}
\tightlist
\item
  Press \texttt{Ctrl+X} to exit, then \texttt{Y} to confirm that you
  want to save the file, then Enter to keep the file name
\end{itemize}

Notice how the \texttt{fastqc} command looks exactly the same as when we
used \texttt{srun}? The main difference between \texttt{srun} and
\texttt{sbatch} is how we package the instructions for the compute node.

\subsubsection{Step 3: Understanding your job
script}\label{step-3-understanding-your-job-script}

In the job script above:

\begin{itemize}
\tightlist
\item
  \texttt{\#!/bin/bash}: this so-called \textbf{shebang} line tells the
  system to run the script with bash. Add it at the very top of every
  job script
\item
  \texttt{\#SBATCH\ -\/-...}: these lines tell SLURM which resources the
  job needs and how to name things. They are the same options that you
  used with \texttt{srun}, plus three new ones:

  \begin{itemize}
  \tightlist
  \item
    \texttt{-\/-job-name}: a name for your job, which you see in
    \texttt{squeue}
  \item
    \texttt{-\/-output}: the file in which SLURM stores everything the
    job prints to the screen (the \textbf{standard output})
  \item
    \texttt{-\/-error}: the file in which SLURM stores error messages
    (the \textbf{standard error})
  \item
    \texttt{\%j} in the file names is replaced by the job ID. This way,
    every job gets its own log files and nothing is overwritten
  \end{itemize}
\item
  \texttt{echo} and \texttt{date}: print messages with the time, so that
  you can follow the progress of the job in the log file
\item
  \texttt{fastqc\ ...}: the actual analysis that runs on the compute
  node
\end{itemize}

Notice that the \texttt{\#SBATCH} lines start with \texttt{\#}? For
bash, these lines are comments. Only SLURM reads them.

\subsubsection{Step 4: Submit and monitor your
job}\label{step-4-submit-and-monitor-your-job}

\begin{Shaded}
\begin{Highlighting}[]
\CommentTok{\# Submit the job script to SLURM}
\ExtensionTok{sbatch}\NormalTok{ scripts/run\_fastqc.sh}

\CommentTok{\# Check the job status (the job may run too fast to appear)}
\ExtensionTok{squeue} \AttributeTok{{-}u} \VariableTok{$USER}

\CommentTok{\# Once the job is finished and no longer in the list, check the outputs}
\FunctionTok{ls} \AttributeTok{{-}l}\NormalTok{ logs}
\FunctionTok{ls} \AttributeTok{{-}l}\NormalTok{ results/fastqc}
\end{Highlighting}
\end{Shaded}

When the job is submitted, you see something like
\texttt{Submitted\ batch\ job\ 754}, and two new log files appear in
your \texttt{logs} folder:

\begin{itemize}
\tightlist
\item
  \texttt{fastqc\_\textless{}jobID\textgreater{}.out}: the standard
  output, e.g.~the messages from \texttt{echo} and \texttt{date}
\item
  \texttt{fastqc\_\textless{}jobID\textgreater{}.err}: the error log.
  Check this file if your job fails
\end{itemize}

Have a look at both log files, for example with
\texttt{cat\ logs/fastqc\_*.out}. Do you see the messages from
\texttt{echo} and \texttt{date}? Some programs also write normal
progress messages into the error log, so a \texttt{.err} file with
content does not always mean that something went wrong.

Since we gave FastQC the same output folder, the reports from the
\texttt{srun} run were replaced by the new ones. Here that is fine,
because the input is the same.

\begin{tcolorbox}[enhanced jigsaw, left=2mm, colframe=quarto-callout-tip-color-frame, toprule=.15mm, arc=.35mm, colback=white, colbacktitle=quarto-callout-tip-color!10!white, opacitybacktitle=0.6, titlerule=0mm, opacityback=0, bottomrule=.15mm, bottomtitle=1mm, toptitle=1mm, title=\textcolor{quarto-callout-tip-color}{\faLightbulb}\hspace{0.5em}{Tip: Debugging your first sbatch jobs}, leftrule=.75mm, breakable, rightrule=.15mm, coltitle=black]

If your job fails:

\begin{itemize}
\tightlist
\item
  Check the \texttt{.err} and \texttt{.out} files in the \texttt{logs}
  folder. These files usually tell you what went wrong
\item
  Check that your input files and paths exist, e.g.~with \texttt{ls}.
  The job runs from the folder in which you typed \texttt{sbatch}, so
  relative paths start from there
\item
  Try to run the main command interactively with \texttt{srun} first. If
  it works there, it should also work in a script
\end{itemize}

\end{tcolorbox}

\subsection{\texorpdfstring{\texttt{sacct}: Checking the resources a job
used}{sacct: Checking the resources a job used}}\label{sacct-checking-the-resources-a-job-used}

After a job has finished, you can check which resources it actually used
with \texttt{sacct}. Replace \texttt{754} with the job ID of your FastQC
job:

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{sacct} \AttributeTok{{-}j}\NormalTok{ 754 }\AttributeTok{{-}{-}format}\OperatorTok{=}\NormalTok{User,JobID,JobName,State,Start,End,Elapsed,MaxRSS,NCPUS}
\end{Highlighting}
\end{Shaded}

Here:

\begin{itemize}
\tightlist
\item
  \texttt{-j\ 754}: show the information for job 754
\item
  \texttt{-\/-format=...}: choose which columns to show. The most useful
  ones are:

  \begin{itemize}
  \tightlist
  \item
    \texttt{State}: whether the job finished successfully (COMPLETED) or
    not (e.g.~FAILED, CANCELLED, TIMEOUT)
  \item
    \texttt{Elapsed}: how long the job ran
  \item
    \texttt{MaxRSS}: the maximum amount of memory the job used. Compare
    this with the memory you requested with \texttt{-\/-mem}
  \item
    \texttt{NCPUS}: the number of CPUs the job had
  \end{itemize}
\end{itemize}

\subsection{Choosing the right amount of
resources}\label{choosing-the-right-amount-of-resources}

When you are just starting, choosing the right amount of CPUs, memory
and run time can be tricky. The resources a job needs vary a lot between
tools and datasets. Here are a few rules of thumb:

\begin{itemize}
\tightlist
\item
  \textbf{Start small}: a lot of tools don't need huge resources,
  especially for small test runs
\item
  \textbf{Check the tool's documentation}: some tools recommend resource
  settings
\item
  \textbf{Test with a small dataset first}: a subset of your data runs
  faster and helps you find and fix problems
\item
  \textbf{Check what your job used}: use \texttt{sacct} (see above) to
  compare what your job used with what you requested. If you plan to run
  similar jobs over and over again, adjust your requests
\item
  \textbf{Be careful with how memory is counted}: \texttt{-\/-mem=4G}
  asks for 4 GB in total for your job, no matter how many CPUs you
  request. \texttt{-\/-mem-per-cpu=4G} instead asks for 4 GB for each
  CPU, so \texttt{-\/-cpus-per-task=4\ -\/-mem-per-cpu=4G} gives you a
  total of 16 GB of memory (4 CPUs * 4 GB)
\item
  \textbf{Adjust step by step}: if your job fails or runs out of memory
  or time, increase the resources gradually
\end{itemize}

Remember: requesting more resources than you need makes your jobs wait
longer in the queue and can block others from running.

\section{\texorpdfstring{\texttt{screen}: Keeping srun jobs running
(optional)}{screen: Keeping srun jobs running (optional)}}\label{screen-keeping-srun-jobs-running-optional}

\begin{tcolorbox}[enhanced jigsaw, left=2mm, colframe=quarto-callout-tip-color-frame, toprule=.15mm, arc=.35mm, colback=white, colbacktitle=quarto-callout-tip-color!10!white, opacitybacktitle=0.6, titlerule=0mm, opacityback=0, bottomrule=.15mm, bottomtitle=1mm, toptitle=1mm, title=\textcolor{quarto-callout-tip-color}{\faLightbulb}\hspace{0.5em}{Using screen for long srun jobs}, leftrule=.75mm, breakable, rightrule=.15mm, coltitle=black]

One downside of \texttt{srun} for long running jobs is that your
terminal is ``blocked'' as long as the job runs, and your job is aborted
if you lose the ssh connection to the HPC. For long running jobs, there
are two ways to deal with this:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  use \texttt{sbatch} (see above)
\item
  run the \texttt{srun} job inside a screen

that you can start a screen session and open any number of windows
(virtual terminals) inside that session. Processes running in a screen
continue to run when their window is not visible, even if you get
disconnected. As long as the server is running, your process continues.

We start a screen as follows:

\end{Highlighting}
\end{Shaded}

\begin{Shaded}

\section{Job arrays: Running many files in parallel
(optional)}\label{job-arrays-running-many-files-in-parallel-optional}

\begin{tcolorbox}[enhanced jigsaw, left=2mm, colframe=quarto-callout-tip-color-frame, toprule=.15mm, arc=.35mm, colback=white, colbacktitle=quarto-callout-tip-color!10!white, opacitybacktitle=0.6, titlerule=0mm, opacityback=0, bottomrule=.15mm, bottomtitle=1mm, toptitle=1mm, title=\textcolor{quarto-callout-tip-color}{\faLightbulb}\hspace{0.5em}{Advanced tip: sbatch arrays to run multiple files in parallel}, leftrule=.75mm, breakable, rightrule=.15mm, coltitle=black]

With FastQC, we are lucky that we can give the tool all fastq files at
once with a wildcard. Not all programs work this way.

For this section, let's assume that we need to give the tool each file
one by one. How would we run such a job efficiently?

We can use a \textbf{job array}, which allows us to:

\begin{itemize}
\tightlist
\item
  Run several jobs that have the same job definition, i.e.~CPUs, memory
  and software
\item
  Run these jobs in parallel (at the same time), instead of one after
  the other
\end{itemize}

Let's start with making a list of the files we want to work with, using
what we learned on day 1:

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{ls}\NormalTok{ data/seq\_project/}\PreprocessorTok{*}\NormalTok{/}\PreprocessorTok{*}\NormalTok{.gz }\KeywordTok{|} \FunctionTok{cut} \AttributeTok{{-}f4} \AttributeTok{{-}d} \StringTok{"/"} \OperatorTok{\textgreater{}}\NormalTok{ samples.txt}

\CommentTok{\# Check the list: we expect 8 file names}
\FunctionTok{cat}\NormalTok{ samples.txt}
\FunctionTok{wc} \AttributeTok{{-}l}\NormalTok{ samples.txt}
\end{Highlighting}
\end{Shaded}

Next, we use this text file in our job array. Store the following in
\texttt{scripts/array.sh}:

\begin{Shaded}
\begin{Highlighting}[]
\CommentTok{\#!/bin/bash}
\CommentTok{\#SBATCH {-}{-}job{-}name=my\_array}
\CommentTok{\#SBATCH {-}{-}output=logs/array\_\%A\_\%a.out}
\CommentTok{\#SBATCH {-}{-}error=logs/array\_\%A\_\%a.err}
\CommentTok{\#SBATCH {-}{-}array=1{-}8}
\CommentTok{\#SBATCH {-}{-}cpus{-}per{-}task=1}
\CommentTok{\#SBATCH {-}{-}mem=5G}

\CommentTok{\# The number of the current job in the array (1 to 8 for our 8 files)}
\VariableTok{INDEX}\OperatorTok{=}\VariableTok{$SLURM\_ARRAY\_TASK\_ID}

\CommentTok{\# Read the file name on line number INDEX of samples.txt}
\VariableTok{CURRENT\_SAMPLE}\OperatorTok{=}\VariableTok{$(}\FunctionTok{sed} \AttributeTok{{-}n} \StringTok{"}\VariableTok{$\{INDEX\}}\StringTok{p"}\NormalTok{ samples.txt}\VariableTok{)}

\CommentTok{\# Print what is happening}
\BuiltInTok{echo} \StringTok{"Now Job}\VariableTok{$\{INDEX\}}\StringTok{ runs on }\VariableTok{$\{CURRENT\_SAMPLE\}}\StringTok{"}

\CommentTok{\# Run the actual job}
\ExtensionTok{fastqc}\NormalTok{ data/seq\_project/}\PreprocessorTok{*}\NormalTok{/}\VariableTok{$\{CURRENT\_SAMPLE\}} \AttributeTok{{-}o}\NormalTok{ results/fastqc }\AttributeTok{{-}{-}threads}\NormalTok{ 1}
\end{Highlighting}
\end{Shaded}

In the script, we use some new SLURM options:

\begin{itemize}
\tightlist
\item
  \texttt{\#SBATCH\ -\/-array=1-8}: sets up a job array with 8 jobs,
  numbered 1 to 8. We choose 1-8 because we have exactly 8 fastq.gz
  files
\item
  \texttt{\#SBATCH\ -\/-output=logs/array\_\%A\_\%a.out}: \texttt{\%A}
  is replaced by the job ID that SLURM assigns, and \texttt{\%a} by the
  number of the job in the array
\item
  \textbf{Important}: do the individual jobs in your array use a lot of
  CPUs or memory? Then you might not want to run all of them at the same
  time. With \texttt{\#SBATCH\ -\/-array=1-8\%2}, SLURM runs at most 2
  jobs at the same time, and starts the next ones when these have
  finished. Try to use no more than \textasciitilde20\% of the
  Crunchomics cluster at the same time.
\end{itemize}

The script does the following:

\begin{itemize}
\tightlist
\item
  \texttt{INDEX} stores the value of \texttt{SLURM\_ARRAY\_TASK\_ID},
  the number of the current job within the array. This is 1 for the
  first job, 2 for the second, \ldots, and 8 for the last one
\item
  \texttt{sed\ -n\ "\$\{INDEX\}p"\ samples.txt} prints one line of
  \texttt{samples.txt}: line 1 for job 1, line 2 for job 2, and so on.
  We store this file name in the variable \texttt{CURRENT\_SAMPLE}. For
  the first job, this is \texttt{Sample-DUMMY1\_R1.fastq.gz}
\item
  \texttt{echo} records which job works on which file
\item
  Finally, we run FastQC on the file stored in \texttt{CURRENT\_SAMPLE}
\end{itemize}

Submit the script with \texttt{sbatch\ scripts/array.sh}. If we check
what is happening right after submitting the job with \texttt{squeue},
we should see something like this:

\includegraphics[width=0.5\linewidth,height=\textheight,keepaspectratio]{../img/arrays.png}

We see that jobs 1-4 are already running, and jobs 5-8 are waiting for
space. That is one of the useful things about a job manager such as
SLURM: it finds the resources on all nodes for us, as long as we
requested sensible amounts of CPUs and memory.

If we check the log files, we should see something like this:

\includegraphics[width=0.5\linewidth,height=\textheight,keepaspectratio]{../img/arrays2.png}

We get an output and an error file for each job. In the output, we see
the value stored in \texttt{INDEX}, here 1, and in
\texttt{CURRENT\_SAMPLE}, here \texttt{Sample-DUMMY1\_R1.fastq.gz}, and
that the analysis finished successfully.

More about arrays and other SLURM options can be found on the
\href{https://scienceparkstudygroup.github.io/ibed-bioinformatics-page/source/cli/slurm_basics.html}{IBED
SLURM basics page}.

\end{tcolorbox}

\section{Installing software}\label{installing-software}

There might be cases where the software you are interested in is not
installed on the HPC you are working with (or on your own computer).

In the majority of cases, you should be able to install software by
using a package management system, such as conda or mamba. These systems
allow you to find and install packages in their own environment without
administrator privileges. Let's have a look at a very brief example:

\subsection{Install conda/mamba}\label{install-condamamba}

A lot of systems already come with conda/mamba installed, however, if
possible we recommend working with mamba instead of conda. mamba is a
replacement and uses the same commands and configuration options as
conda, however, it tends to be much faster. A useful thing is that if
you find documentation for conda then you can swap almost all commands
between conda \& mamba.

You can check if you have either with:

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{which}\NormalTok{ conda}
\FunctionTok{which}\NormalTok{ mamba}
\end{Highlighting}
\end{Shaded}

If you have conda installed and do not want to install anything else,
that is fine. Just replace all instances of mamba with conda below.

If you don't have access to either conda or mamba then you can install
Miniforge (which includes conda and mamba by default) by running the
following two commands:

\begin{Shaded}
\begin{Highlighting}[]

When you run a script or a command, it operates in its own environment.
The source command is like telling the script to look into another file,
in this case, \texttt{\textasciitilde{}/.bashrc}, and execute the
commands in that file as if they were written directly into the script.

to execute the commands in the \texttt{\textasciitilde{}/.bashrc} file.

activate any software or tools that are required for the script to run
successfully. In our case this tells Slurm where we have installed conda
and thus enables Slurm to use conda itself.

environment using \texttt{mamba\ activate\ seqkit\_2.6.1}. This ensures
that the SeqKit tool and its dependencies are available and properly
configured for use in the subsequent part of the script.
