\chapter{Using an HPC}\label{using-an-hpc}

Now that you are more familiar with the command line, we will learn how
to work on the UvA Crunchomics HPC. On this page, you will:

\begin{itemize}
\tightlist
\item
  Connect to Crunchomics and prepare your account
\item
  Transfer the sequencing data from your own computer to Crunchomics
\item
  Run your first analyses on the compute nodes with SLURM:

  \begin{itemize}
  \tightlist
  \item
    \texttt{srun} for short, interactive analyses
  \item
    \texttt{sbatch} for longer running, more resource intensive analyses
  \end{itemize}
\item
  Install your own software with conda
\item
  Keep documenting what you do in the notebook (\texttt{notes.md}) that
  you started on day 1
\end{itemize}

For people following this tutorial outside of UvA:

\begin{itemize}
\tightlist
\item
  If you have access to an HPC that uses SLURM, you can still follow the
  tutorial
\item
  If you do not have access to an HPC but are interested in how to
  install and run software that can be used to analyse sequencing data,
  you still might want to check out the steps below. The dataset is very
  small and all analyses can be run on a desktop computer
\end{itemize}

\section{Connecting to the HPC}\label{connecting-to-the-hpc}

\subsection{\texorpdfstring{\texttt{ssh}: Connecting to a
server}{ssh: Connecting to a server}}\label{ssh-connecting-to-a-server}

\textbf{SSH} (Secure Shell) is a network protocol that allows you to
securely connect to a remote computer, such as the Crunchomics HPC. The
general command looks like this:

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{ssh}\NormalTok{ username@server}
\end{Highlighting}
\end{Shaded}

Here:

\begin{itemize}
\tightlist
\item
  \texttt{username} is your account name on the HPC. For Crunchomics,
  this is your UvAnetID
\item
  \texttt{server} is the address of the HPC you want to connect to. For
  Crunchomics, this is \texttt{omics-h0.science.uva.nl}
\end{itemize}

To log in to Crunchomics, use the following command and enter your UvA
password when you are asked for it. Remember that nothing appears on the
screen while you type your password:

\begin{Shaded}
\begin{Highlighting}[]
\CommentTok{\# Log in to Crunchomics (replace uvanetid with your own UvAnetID)}
\FunctionTok{ssh}\NormalTok{ uvanetid@omics{-}h0.science.uva.nl}
\end{Highlighting}
\end{Shaded}

You did the same during the \href{installation.qmd}{Before you start}
checks. After logging in, the prompt changes: it now shows your UvAnetID
and \texttt{omics-h0}. Every command you type now runs on Crunchomics,
not on your own computer.

\begin{tcolorbox}[enhanced jigsaw, colbacktitle=quarto-callout-important-color!10!white, rightrule=.15mm, bottomrule=.15mm, opacitybacktitle=0.6, toptitle=1mm, colframe=quarto-callout-important-color-frame, arc=.35mm, toprule=.15mm, titlerule=0mm, title=\textcolor{quarto-callout-important-color}{\faExclamation}\hspace{0.5em}{Important}, bottomtitle=1mm, breakable, colback=white, left=2mm, leftrule=.75mm, opacityback=0, coltitle=black]

\textbf{Important tips for connecting:}

\begin{itemize}
\tightlist
\item
  If you want to log in to Crunchomics while working from UvA, use the
  eduroam network, not the open Amsterdam Science Park network
\item
  If you are connecting from outside UvA, you must be connected to the
  VPN. Contact ICT if you have not set it up or encounter issues
\item
  Always double-check your username and the server address to avoid
  login errors
\end{itemize}

\end{tcolorbox}

\begin{tcolorbox}[enhanced jigsaw, colbacktitle=quarto-callout-tip-color!10!white, rightrule=.15mm, bottomrule=.15mm, opacitybacktitle=0.6, toptitle=1mm, colframe=quarto-callout-tip-color-frame, arc=.35mm, toprule=.15mm, titlerule=0mm, title=\textcolor{quarto-callout-tip-color}{\faLightbulb}\hspace{0.5em}{Tip: Viewing graphical output with ssh -X (optional)}, bottomtitle=1mm, breakable, colback=white, left=2mm, leftrule=.75mm, opacityback=0, coltitle=black]

Some programs on the HPC can open a window, for example to show a plot
or a PDF. To see such windows on your own computer, log in with the
\texttt{-X} option:

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{ssh} \AttributeTok{{-}X}\NormalTok{ uvanetid@omics{-}h0.science.uva.nl}
\end{Highlighting}
\end{Shaded}

\texttt{-X} enables what is called \textbf{X11 forwarding}: the HPC
sends the graphical output to your computer. In this tutorial we don't
need this, because we copy the results to our own computer instead.

\end{tcolorbox}

\subsection{Crunchomics: Preparing your
account}\label{crunchomics-preparing-your-account}

If this is your \textbf{first time using Crunchomics}, you need to run a
small bash script to set up your account. Ignore this section if you
have done this before. The script:

\begin{itemize}
\tightlist
\item
  Adds \texttt{/zfs/omics/software/bin} to your PATH. The \textbf{PATH}
  is the list of folders in which bash looks for programs. With this
  change, bash can find the software that is already installed on
  Crunchomics
\item
  Sets up a Python 3 environment with some useful Python packages
\item
  Creates a link called \texttt{personal} in your home directory. This
  link leads to your personal directory, which has 500 GB of space. Your
  home directory itself only has 25 GB
\end{itemize}

To set up your account, run the following commands:

\begin{Shaded}
\begin{Highlighting}[]
\CommentTok{\# First, orient yourself}
\BuiltInTok{pwd}
\FunctionTok{ls} \AttributeTok{{-}lh}

\CommentTok{\# Run the Crunchomics installation script}
\ExtensionTok{/zfs/omics/software/script/omics\_install\_script}

\CommentTok{\# Check what changed}
\CommentTok{\# You should now see the personal folder inside your home directory}
\FunctionTok{ls} \AttributeTok{{-}lh}
\end{Highlighting}
\end{Shaded}

After the script, \texttt{ls\ -lh} prints a line like this (your date
and group name can differ):

\begin{verbatim}
lrwxrwxrwx.  1 username sils-omics-unix-fnwi 27 Sep  4  2023 personal -> /zfs/omics/personal/username
\end{verbatim}

The arrow (\texttt{-\textgreater{}}) tells you that \texttt{personal} is
not a normal folder. We come back to this in the next section.

\subsection{Preparing your working
directory}\label{preparing-your-working-directory}

Next, let's make a project folder for our analyses. Always make project
folders inside your personal directory, since it has much more space
than your home directory. We give the folder the same name as on our own
computer, \texttt{data\_analysis}:

\begin{Shaded}
\begin{Highlighting}[]
\CommentTok{\# Go into the personal folder}
\BuiltInTok{cd}\NormalTok{ personal}

\CommentTok{\# Make a new project folder and go into it}
\FunctionTok{mkdir}\NormalTok{ data\_analysis}
\BuiltInTok{cd}\NormalTok{ data\_analysis}

\CommentTok{\# Check that you are in the right folder}
\BuiltInTok{pwd}
\end{Highlighting}
\end{Shaded}

\texttt{pwd} prints \texttt{/home/username/personal/data\_analysis}, so
it looks like you are in your home directory. But your files are not
stored there. \texttt{personal} is a \textbf{link} (also called a
\textbf{symbolic link} or \textbf{symlink}): a shortcut that points to
another folder, here \texttt{/zfs/omics/personal/username}. That is what
the arrow in the \texttt{ls\ -lh} output showed. So
\texttt{\textasciitilde{}/personal/data\_analysis} and
\texttt{/zfs/omics/personal/username/data\_analysis} are two paths to
the same folder:

You now have a clean workspace for all the analyses that you will run on
Crunchomics. As on your own computer, it is good practice to keep your
raw data, results and scripts in separate folders.

\subsection{\texorpdfstring{\texttt{scp}: Transferring data to and from
a
server}{scp: Transferring data to and from a server}}\label{scp-transferring-data-to-and-from-a-server}

Next, we want to transfer the \texttt{data} folder with our sequencing
data from our own computer to the new project folder on Crunchomics. We
do this with \texttt{scp} (Secure Copy Protocol), which securely copies
files and folders between your computer and a remote server.

The basic syntax is:

\begin{itemize}
\tightlist
\item
  \texttt{scp\ {[}options{]}\ SOURCE\ DESTINATION}
\item
  A location on a server is written as
  \texttt{username@server:path\_on\_the\_server}
\end{itemize}

When transferring data, you must \textbf{run \texttt{scp} in a terminal
on your own computer}, not in a terminal that is logged in to the HPC.
To keep yourself organized, it is useful to have two terminals open: one
on your own computer and one on Crunchomics. In MobaXterm, you can open
a second terminal in a new tab:

To copy the entire \texttt{data} folder into your Crunchomics project
folder, use:

\begin{Shaded}
\begin{Highlighting}[]
\CommentTok{\# Run this in the terminal on your OWN computer (not on the HPC),}
\CommentTok{\# from inside your local data\_analysis folder (where the data folder is)}
\CommentTok{\# Replace both instances of \textquotesingle{}username\textquotesingle{} with your UvAnetID}
\FunctionTok{scp} \AttributeTok{{-}r}\NormalTok{ data username@omics{-}h0.science.uva.nl:/home/username/personal/data\_analysis}
\end{Highlighting}
\end{Shaded}

Here:

\begin{itemize}
\tightlist
\item
  \texttt{-r} copies a folder together with everything inside it
  (\textbf{recursive}). Without \texttt{-r}, \texttt{scp} only copies
  single files
\item
  \texttt{data} is the source: the folder on your own computer
\item
  \texttt{username@omics-h0.science.uva.nl:/home/username/personal/data\_analysis}
  is the destination: your project folder on Crunchomics
\end{itemize}

Now switch to the terminal that is logged in to Crunchomics and check
that the files arrived:

\begin{Shaded}
\begin{Highlighting}[]
\CommentTok{\# Run this on Crunchomics, inside the data\_analysis folder}
\FunctionTok{ls} \AttributeTok{{-}l}\NormalTok{ data/seq\_project/}\PreprocessorTok{*}\NormalTok{/}\PreprocessorTok{*}\NormalTok{fastq.gz}

\CommentTok{\# We expect 8 files (4 samples, R1 and R2 each)}
\FunctionTok{ls}\NormalTok{ data/seq\_project/}\PreprocessorTok{*}\NormalTok{/}\PreprocessorTok{*}\NormalTok{fastq.gz }\KeywordTok{|} \FunctionTok{wc} \AttributeTok{{-}l}
\end{Highlighting}
\end{Shaded}

\begin{tcolorbox}[enhanced jigsaw, colbacktitle=quarto-callout-tip-color!10!white, rightrule=.15mm, bottomrule=.15mm, opacitybacktitle=0.6, toptitle=1mm, colframe=quarto-callout-tip-color-frame, arc=.35mm, toprule=.15mm, titlerule=0mm, title=\textcolor{quarto-callout-tip-color}{\faLightbulb}\hspace{0.5em}{Tip: Moving data from the HPC to your own computer (optional)}, bottomtitle=1mm, breakable, colback=white, left=2mm, leftrule=.75mm, opacityback=0, coltitle=black]

You can also copy results from the HPC to your own computer. For this,
you switch source and destination. For example, to copy a single
sequencing file from Crunchomics:

\begin{itemize}
\tightlist
\item
  We do not need \texttt{-r}, since we only copy a single file
\item
  We again run this command in a terminal on our own computer, not on
  the HPC
\item
  The \texttt{.} at the end means ``copy into the folder I am in right
  now'' on your own computer. If you want to copy the file elsewhere,
  replace \texttt{.} with a path
\end{itemize}

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{scp}\NormalTok{ username@omics{-}h0.science.uva.nl:/home/username/personal/data\_analysis/data/seq\_project/barcode001\_User1\_ITS\_1\_L001/Sample{-}DUMMY1\_R1.fastq.gz .}
\end{Highlighting}
\end{Shaded}

\end{tcolorbox}

\begin{tcolorbox}[enhanced jigsaw, colbacktitle=quarto-callout-tip-color!10!white, rightrule=.15mm, bottomrule=.15mm, opacitybacktitle=0.6, toptitle=1mm, colframe=quarto-callout-tip-color-frame, arc=.35mm, toprule=.15mm, titlerule=0mm, title=\textcolor{quarto-callout-tip-color}{\faLightbulb}\hspace{0.5em}{Tip: Moving files with wildcards (optional)}, bottomtitle=1mm, breakable, colback=white, left=2mm, leftrule=.75mm, opacityback=0, coltitle=black]

We can also copy several files at once with a wildcard. Then
\texttt{scp} copies only the files, not the folders they are in.

\begin{Shaded}
\begin{Highlighting}[]
\CommentTok{\# On Crunchomics: make a folder to copy the data into}
\FunctionTok{mkdir}\NormalTok{ transfer\_test}

\CommentTok{\# On your own computer: copy all fastq.gz files to the new folder on Crunchomics}
\FunctionTok{scp}\NormalTok{ data/seq\_project/barcode00}\PreprocessorTok{*}\NormalTok{/}\PreprocessorTok{*}\NormalTok{fastq.gz username@omics{-}h0.science.uva.nl:/home/username/personal/data\_analysis/transfer\_test}

\CommentTok{\# On Crunchomics: view the data}
\CommentTok{\# See how the folder structure is different compared to our first example?}
\FunctionTok{ls} \AttributeTok{{-}l}\NormalTok{ transfer\_test/}\PreprocessorTok{*}
\end{Highlighting}
\end{Shaded}

\textbf{Notice for Mac users}:

For Mac users who work with the zsh shell, the command above might not
work, and you might get an error like ``file not found'', ``no matches
found'' or something similar. That is because zsh handles wildcards
slightly differently than bash. If you see this error and you are sure
that the files exist, try this version of the command:

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{\textbackslash{}scp}\NormalTok{ data/seq\_project/barcode00}\PreprocessorTok{*}\NormalTok{/}\PreprocessorTok{*}\NormalTok{fastq.gz username@omics{-}h0.science.uva.nl:/home/username/personal/data\_analysis/transfer\_test}
\end{Highlighting}
\end{Shaded}

If that does not work, these are some other things to try (different zsh
setups might need slightly different solutions):

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{noglob}\NormalTok{ scp data/seq\_project/barcode00}\PreprocessorTok{*}\NormalTok{/}\PreprocessorTok{*}\NormalTok{fastq.gz username@omics{-}h0.science.uva.nl:/home/username/personal/data\_analysis/transfer\_test}

\FunctionTok{scp} \StringTok{\textquotesingle{}data/seq\_project/barcode00*/*fastq.gz\textquotesingle{}}\NormalTok{ username@omics{-}h0.science.uva.nl:/home/username/personal/data\_analysis/transfer\_test}
\end{Highlighting}

\section{Submitting jobs with SLURM}\label{submitting-jobs-with-slurm}

\subsection{Login node and compute
nodes}\label{login-node-and-compute-nodes}

In the HPC introduction, you learned that an HPC has two main parts:

\begin{itemize}
\tightlist
\item
  The \textbf{login node}: where you log in and do light work, such as
  moving files, editing scripts or preparing jobs
\item
  The \textbf{compute nodes}: where the actual analyses run. These nodes
  have more CPUs and memory
\end{itemize}

We do not run big analyses on the login node. Instead, we send them to
the compute nodes as \textbf{jobs}. A job is a task that you ask the HPC
to run, together with the resources it needs. The jobs are managed by
\textbf{SLURM}, a workload manager that decides \emph{when},
\emph{where} and \emph{how} your jobs run based on the available
resources.

\subsection{\texorpdfstring{\texttt{squeue}: View the jobs in the
queue}{squeue: View the jobs in the queue}}\label{squeue-view-the-jobs-in-the-queue}

The command below shows you which jobs are currently running or waiting
in the queue:

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{squeue}
\end{Highlighting}
\end{Shaded}

This shows all jobs on the system and might look something like this:

\includegraphics[width=0.5\linewidth,height=\textheight,keepaspectratio]{../img/squeue.png}\hfill

Some useful columns to know:

\begin{itemize}
\tightlist
\item
  JOBID: a unique number for each job. You can use it to check on or
  cancel a job later
\item
  ST: the current state of the job, e.g.~R = running, PD = pending
  (waiting). A full list of SLURM job state codes can be found
  \href{https://curc.readthedocs.io/en/latest/running-jobs/squeue-status-codes.html}{here}
\end{itemize}

Once you have submitted a job, it appears in this list as well. To see
only your own jobs, add the \texttt{-u} option followed by your user
name. \texttt{\$USER} is a shortcut that bash replaces with your own
user name:

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{squeue} \AttributeTok{{-}u} \VariableTok{$USER}
\end{Highlighting}
\end{Shaded}

\subsection{\texorpdfstring{\texttt{srun}: Submitting a job
interactively}{srun: Submitting a job interactively}}\label{srun-submitting-a-job-interactively}

Now let's run our first job on a compute node. There are two main ways
to submit jobs: \texttt{srun} and \texttt{sbatch}. We start with
\texttt{srun}, which you typically use when:

\begin{itemize}
\tightlist
\item
  You want to run tasks \textbf{interactively} and see the output
  directly on your screen
\item
  You are \textbf{testing or debugging} your commands before writing a
  job script
\item
  You have \textbf{short jobs} (usually less than a few hours)
\end{itemize}

Let's start with a very simple example to see how \texttt{srun} works:

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{srun} \AttributeTok{{-}{-}cpus{-}per{-}task}\OperatorTok{=}\NormalTok{1 }\AttributeTok{{-}{-}mem}\OperatorTok{=}\NormalTok{1G }\AttributeTok{{-}{-}time}\OperatorTok{=}\NormalTok{00:10:00 echo }\StringTok{"Hello world"}
\end{Highlighting}
\end{Shaded}

Here's what each part means:

\begin{itemize}
\tightlist
\item
  \texttt{srun}: tells SLURM that you want to run something on a compute
  node, with the resources that follow
\item
  \texttt{-\/-cpus-per-task=1}: request 1 CPU
\item
  \texttt{-\/-mem=1G}: request 1 GB of memory
\item
  \texttt{-\/-time=00:10:00}: set a maximum run time of 10 minutes
  (hours:minutes:seconds). If the job takes longer, SLURM stops it
\item
  \texttt{echo\ "Hello\ world"}: the actual command to run
\end{itemize}

So everything between \texttt{srun} and the actual command tells SLURM
which resources your job needs on the compute node. The job runs so fast
that you won't see it in \texttt{squeue}. But congratulations, after
submitting this, you just communicated with a compute node for the first
time.

\begin{tcolorbox}[enhanced jigsaw, colbacktitle=quarto-callout-important-color!10!white, rightrule=.15mm, bottomrule=.15mm, opacitybacktitle=0.6, toptitle=1mm, colframe=quarto-callout-important-color-frame, arc=.35mm, toprule=.15mm, titlerule=0mm, title=\textcolor{quarto-callout-important-color}{\faExclamation}\hspace{0.5em}{Important}, bottomtitle=1mm, breakable, colback=white, left=2mm, leftrule=.75mm, opacityback=0, coltitle=black]

Jobs started with \texttt{srun} stop if you lose the connection to the
HPC, for example when you close your laptop. For longer jobs, use
\texttt{sbatch} (see below).

\end{tcolorbox}

\subsection{\texorpdfstring{Run seqkit stats with
\texttt{srun}}{Run seqkit stats with srun}}\label{run-seqkit-stats-with-srun}

Next, let's use \texttt{srun} for something more useful.
\href{https://bioinf.shenwei.me/seqkit/}{SeqKit} is a toolkit for
working with sequence files, and it is already installed on Crunchomics
(version 2.7.0). Its command \texttt{seqkit\ stats} gives a summary of
each fastq file: how many reads it has, how long they are, and how good
their quality is. We use it to get a first overview of the sequencing
data that we just copied to Crunchomics.

Whenever you use a tool for the first time, check its help page
(e.g.~\texttt{seqkit\ stats\ -h}) to see all available options, or look
online for a manual.

\begin{Shaded}
\begin{Highlighting}[]
\CommentTok{\# Make a results folder with a seqkit folder inside}
\FunctionTok{mkdir} \AttributeTok{{-}p}\NormalTok{ results/seqkit}

\CommentTok{\# Run seqkit stats on all fastq.gz files with srun}
\ExtensionTok{srun} \AttributeTok{{-}{-}cpus{-}per{-}task}\OperatorTok{=}\NormalTok{1 }\AttributeTok{{-}{-}mem}\OperatorTok{=}\NormalTok{5G }\AttributeTok{{-}{-}time}\OperatorTok{=}\NormalTok{00:30:00 seqkit stats }\AttributeTok{{-}b} \AttributeTok{{-}a} \AttributeTok{{-}T} \AttributeTok{{-}o}\NormalTok{ results/seqkit/stats\_raw.txt data/seq\_project/}\PreprocessorTok{*}\NormalTok{/}\PreprocessorTok{*}\NormalTok{gz }\AttributeTok{{-}{-}threads}\NormalTok{ 1}

\CommentTok{\# Check the output: we expect one table with a header line and one line per fastq.gz file}
\FunctionTok{wc} \AttributeTok{{-}l}\NormalTok{ results/seqkit/stats\_raw.txt}
\end{Highlighting}
\end{Shaded}

Here:

\begin{itemize}
\tightlist
\item
  \texttt{seqkit\ stats\ data/seq\_project/*/*gz}: run
  \texttt{seqkit\ stats} on all files in the \texttt{seq\_project}
  folders that end with \texttt{gz}
\item
  \texttt{-b}: only output the basename of files instead of printing the
  relative path to the fastq.gz files
\item
  \texttt{-a}: print all statistics. Without it, seqkit prints only the
  basic ones, such as the number and length of the reads, but not their
  quality
\item
  \texttt{-T}: print the output as a table in which the columns are
  separated by tabs. This format is easy to read for other commands,
  such as \texttt{cut}
\item
  \texttt{-o\ results/seqkit/stats\_raw.txt}: write the output into this
  file.
\item
  \texttt{-\/-threads\ 1}: let seqkit use 1 CPU (in our case, thread and
  CPU mean the same)

  \begin{itemize}
  \tightlist
  \item
    \textbf{Important}: always make sure that the number of CPUs you
    request from SLURM matches the number of CPUs (threads) the software
    uses. If the tool uses more than you requested, it competes with
    itself for CPUs. If you request more than the tool uses, the extra
    CPUs sit idle while others could use them
  \end{itemize}
\end{itemize}

Since we work with little data, this runs fast despite only using 1 CPU.
It may even finish within a few seconds. If you are logged in to
Crunchomics in a second terminal and run \texttt{squeue} while your job
is running, you should see it (in the example below, the job is named
after the software and got the job ID 379646):

\includegraphics[width=0.5\linewidth,height=\textheight,keepaspectratio]{../img/squeue2.png}\hfill

It is a good habit to look at the outputs of whatever software to run,
not only to understand your data but also to make sure that the software
ran correctly:

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{cat}\NormalTok{ results/seqkit/stats\_raw.txt}
\end{Highlighting}
\end{Shaded}

The output should look like this:

\includegraphics[width=1\linewidth,height=\textheight,keepaspectratio]{../img/seqkit_out.png}\hfill

The most useful columns for us are:

\begin{itemize}
\tightlist
\item
  \texttt{num\_seqs}: the number of reads in the file
\item
  \texttt{min\_len}, \texttt{avg\_len} and \texttt{max\_len}: the
  shortest, average and longest read length
\item
  \texttt{Q20(\%)} and \texttt{Q30(\%)}: the percentage of bases with a
  quality score of at least 20 or 30. A quality score of 20 means that

\end{itemize}

\subsection{\texorpdfstring{\texttt{sbatch}: Submitting a long-running
job}{sbatch: Submitting a long-running job}}\label{sbatch-submitting-a-long-running-job}

While \texttt{srun} is great for quick, interactive runs, most analyses
on an HPC are submitted with \textbf{\texttt{sbatch}}. With
\texttt{sbatch}, you write your commands into a \textbf{job script}, a
text file with all the commands and the resources your job needs. SLURM
then runs the script in the background, even after you log out.

Use \texttt{sbatch} when:

\begin{itemize}
\tightlist
\item
  You have \textbf{long or resource-intensive} analyses
\item
  You want jobs to run \textbf{unattended}, without your direct
  supervision
\item
  You want to \textbf{run several jobs} after each other or at the same
  time
\end{itemize}

\subsubsection{Step 1: Create folders for scripts and
logs}\label{step-1-create-folders-for-scripts-and-logs}

We keep our project tidy by making separate folders for our job scripts
and for the log files that SLURM writes:

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{mkdir} \AttributeTok{{-}p}\NormalTok{ scripts logs}

\CommentTok{\# Check that the folders are there}
\FunctionTok{ls} \AttributeTok{{-}l}
\end{Highlighting}
\end{Shaded}

\subsubsection{Step 2: Write a job
script}\label{step-2-write-a-job-script}

We run \texttt{seqkit\ stats} again, but this time with \texttt{sbatch}
instead of \texttt{srun}, so that you can directly compare the two.

Use \texttt{nano} to create a script file:

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{nano}\NormalTok{ scripts/seqkit.sh}
\end{Highlighting}
\end{Shaded}

Then add the following content inside that file:

\begin{Shaded}
\begin{Highlighting}[]
\CommentTok{\#!/bin/bash}
\CommentTok{\#SBATCH {-}{-}job{-}name=seqkit}
\CommentTok{\#SBATCH {-}{-}output=logs/seqkit\_\%j.out}
\CommentTok{\#SBATCH {-}{-}error=logs/seqkit\_\%j.err}
\CommentTok{\#SBATCH {-}{-}cpus{-}per{-}task=1}
\CommentTok{\#SBATCH {-}{-}mem=5G}
\CommentTok{\#SBATCH {-}{-}time=01:00:00}

\BuiltInTok{echo} \StringTok{"seqkit job started on:"}
\FunctionTok{date}

\ExtensionTok{seqkit}\NormalTok{ stats }\AttributeTok{{-}b} \AttributeTok{{-}a} \AttributeTok{{-}T} \AttributeTok{{-}o}\NormalTok{ results/seqkit/stats\_raw.txt data/seq\_project/}\PreprocessorTok{*}\NormalTok{/}\PreprocessorTok{*}\NormalTok{gz }\AttributeTok{{-}{-}threads}\NormalTok{ 1}

\BuiltInTok{echo} \StringTok{"seqkit job finished on:"}
\FunctionTok{date}
\end{Highlighting}
\end{Shaded}

Save and exit:

\begin{itemize}
\tightlist
\item
  Press \texttt{Ctrl+X} to exit, then \texttt{Y} to confirm that you
  want to save the file, then Enter to keep the file name
\end{itemize}

Notice how the \texttt{seqkit\ stats} command looks exactly the same as
when we used \texttt{srun}? The main difference between \texttt{srun}
and \texttt{sbatch} is how we package the instructions for the compute
node.

\subsubsection{Step 3: Understanding your job
script}\label{step-3-understanding-your-job-script}

In the job script above:

\begin{itemize}
\tightlist
\item
  \texttt{\#!/bin/bash}: this so-called \textbf{shebang} line tells the
  system to run the script with bash. Add it at the very top of every
  job script
\item
  \texttt{\#SBATCH\ -\/-...}: these lines tell SLURM which resources the
  job needs and how to name things. They are the same options that you
  used with \texttt{srun}, plus three new ones:

  \begin{itemize}
  \tightlist
  \item
    \texttt{-\/-job-name}: a name for your job, which you see in
    \texttt{squeue}
  \item
    \texttt{-\/-output}: the file in which SLURM stores everything the
    job prints to the screen (the \textbf{standard output})
  \item
    \texttt{-\/-error}: the file in which SLURM stores error messages
    (the \textbf{standard error})

\end{itemize}

\subsection{Choosing the right amount of
resources}\label{choosing-the-right-amount-of-resources}

When you are just starting, choosing the right amount of CPUs, memory
and run time can be tricky. The resources a job needs vary a lot between
tools and datasets. Here are a few rules of thumb:

\begin{itemize}
\tightlist
\item
  \textbf{Start small}: a lot of tools don't need huge resources,
  especially for small test runs
\item
  \textbf{Check the tool's documentation}: some tools recommend resource
  settings
\item
  \textbf{Test with a small dataset first}: a subset of your data runs
  faster and helps you find and fix problems
\item
  \textbf{Be careful with how memory is counted}: \texttt{-\/-mem=4G}
  asks for 4 GB in total for your job, no matter how many CPUs you
  request. \texttt{-\/-mem-per-cpu=4G} instead asks for 4 GB for each
  CPU, so \texttt{-\/-cpus-per-task=4\ -\/-mem-per-cpu=4G} gives you a
  total of 16 GB of memory (4 CPUs * 4 GB)
\end{itemize}

Remember: requesting more resources than you need makes your jobs wait
longer in the queue and can block others from running.

If you want to know how much a finished job actually used, have a look
at the optional \texttt{sacct} box below.

\begin{tcolorbox}[enhanced jigsaw, colbacktitle=quarto-callout-tip-color!10!white, rightrule=.15mm, bottomrule=.15mm, opacitybacktitle=0.6, toptitle=1mm, colframe=quarto-callout-tip-color-frame, arc=.35mm, toprule=.15mm, titlerule=0mm, title=\textcolor{quarto-callout-tip-color}{\faLightbulb}\hspace{0.5em}{Tip: Checking the resources a job used with sacct (optional)}, bottomtitle=1mm, breakable, colback=white, left=2mm, leftrule=.75mm, opacityback=0, coltitle=black]

After a job has finished, you can check which resources it actually used
with \texttt{sacct}. Replace \texttt{379723} with the job ID of your
seqkit job:

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{sacct} \AttributeTok{{-}j}\NormalTok{ 379723 }\AttributeTok{{-}{-}format}\OperatorTok{=}\NormalTok{User,JobID,JobName,State,Start,End,Elapsed,MaxRSS,NCPUS}
\end{Highlighting}
\end{Shaded}

Here:

\begin{itemize}
\tightlist
\item
  \texttt{-j\ 379723}: show the information for job 379723
\item
  \texttt{-\/-format=...}: choose which columns to show. The most useful
  ones are:

  \begin{itemize}
  \tightlist
  \item
    \texttt{State}: whether the job finished successfully (COMPLETED) or
    not (e.g.~FAILED, CANCELLED, TIMEOUT)
  \item
    \texttt{Elapsed}: how long the job ran
  \item
    \texttt{MaxRSS}: the maximum amount of memory the job used. Compare
    this with the memory you requested with \texttt{-\/-mem}
  \item
    \texttt{NCPUS}: the number of CPUs the job had
  \end{itemize}
\end{itemize}

How to use this information:

\begin{itemize}
\tightlist
\item
  \textbf{Compare what your job used with what you requested}: if you
  plan to run similar jobs over and over again, adjust your requests
\item
  \textbf{Adjust step by step}: if your job fails or runs out of memory
  or time, increase the resources gradually
\end{itemize}

\section{\texorpdfstring{\texttt{conda}: Installing your own
software}{conda: Installing your own software}}\label{conda-installing-your-own-software}

Crunchomics already has a lot of software installed, but it doesn't have
every tool, and not always comes with the version you need. Let's look
at fastp, the tool we use in the next section:

\begin{Shaded}
\begin{Highlighting}[]
\CommentTok{\# Which fastp does bash find, and which version is it?}
\FunctionTok{which}\NormalTok{ fastp}
\ExtensionTok{fastp} \AttributeTok{{-}{-}version}
\end{Highlighting}
\end{Shaded}

We see that fastp is installed on Crunchomics and that it comes with
version 1.0.1. If we search online, we can find that the newest version
is 1.4.0 (at least when I checked in October 2026). Newer versions fix
errors and add features, and the version you use can change your
results. That is why you should always write down which version of a
tool you used, and why you sometimes want to install a specific version
yourself.

You can't install software into the shared software folders of
Crunchomics, because you don't have administrator rights there. However,
we can use \textbf{conda}: a program that installs software into your
own folders, without administrator rights. \textbf{mamba} does the same
as conda, but faster. It understands the same commands, so you can swap
\texttt{conda} and \texttt{mamba} in almost all commands that you find
online.

conda installs each tool into its own \textbf{environment}: a separate
folder with the tool and all the other programs it needs, in exactly the
right versions. This way, tools that need different versions of the same
program don't get in each other's way. To use a tool, you
\textbf{activate} its environment. Activating adds the environment's
folder to the front of your PATH (remember, the list of folders in which
bash looks for programs), so bash finds the tool there first.

\subsection{Install Miniforge}\label{install-miniforge}

\section{fastp: Running a tool for each sample with a
for-loop}\label{fastp-running-a-tool-for-each-sample-with-a-for-loop}

With \texttt{seqkit\ stats}, we were lucky: we could give it all fastq
files at once with a wildcard. Many tools don't work this way and
instead work on one sample at a time.
\href{https://github.com/OpenGene/fastp}{fastp} is such a tool. It
removes low-quality parts of reads and leftover adapter sequences, which
is called \textbf{trimming} or \textbf{quality filtering}. For
paired-end data, fastp needs the R1 and the R2 file of the same sample
together.

To run fastp on all our samples, we combine three things from day 1:
\texttt{cut} to make a list of samples, a for-loop to repeat the command
for each sample, and a script file to run the loop as a job. We build
the loop step by step, and look at what happens after each step.

If it is not active yet, activate the conda environment with fastp that
we made in the previous section:

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{conda}\NormalTok{ activate fastp\_1.4.0}
\end{Highlighting}
\end{Shaded}

\subsection{Step 1: Run fastp on one
sample}\label{step-1-run-fastp-on-one-sample}

Before we write a loop, we run the tool on a single sample. This shows
us what fastp needs as input and what it produces. Like for every new
tool, start with the help page:

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{fastp} \AttributeTok{{-}{-}help}
\end{Highlighting}
\end{Shaded}

Now let's run fastp on Sample-DUMMY1:

\begin{Shaded}
\begin{Highlighting}[]
\CommentTok{\# Make a folder for the fastp results}
\FunctionTok{mkdir} \AttributeTok{{-}p}\NormalTok{ results/fastp}

\CommentTok{\# Run fastp on the R1 and R2 file of the first sample}
\ExtensionTok{srun} \AttributeTok{{-}{-}cpus{-}per{-}task}\OperatorTok{=}\NormalTok{2 }\AttributeTok{{-}{-}mem}\OperatorTok{=}\NormalTok{5G }\AttributeTok{{-}{-}time}\OperatorTok{=}\NormalTok{00:30:00 fastp }\DataTypeTok{\textbackslash{}}
    \AttributeTok{{-}i}\NormalTok{ data/seq\_project/barcode001\_User1\_ITS\_1\_L001/Sample{-}DUMMY1\_R1.fastq.gz }\DataTypeTok{\textbackslash{}}
    \AttributeTok{{-}I}\NormalTok{ data/seq\_project/barcode001\_User1\_ITS\_1\_L001/Sample{-}DUMMY1\_R2.fastq.gz }\DataTypeTok{\textbackslash{}}
    \AttributeTok{{-}o}\NormalTok{ results/fastp/Sample{-}DUMMY1\_R1.trimmed.fastq.gz }\DataTypeTok{\textbackslash{}}
    \AttributeTok{{-}O}\NormalTok{ results/fastp/Sample{-}DUMMY1\_R2.trimmed.fastq.gz }\DataTypeTok{\textbackslash{}}
    \AttributeTok{{-}{-}thread}\NormalTok{ 2}

\CommentTok{\# Check what fastp made, in the results folder and in the current folder}
\FunctionTok{ls} \AttributeTok{{-}l}\NormalTok{ results/fastp}
\FunctionTok{ls} \AttributeTok{{-}l}
\end{Highlighting}
\end{Shaded}

This command is long, so we split it over several lines to make it more
readable. The \texttt{\textbackslash{}} at the end of a line tells bash
that the command continues on the next line. Be careful: the
\texttt{\textbackslash{}} must be the very last character on the line,
so don't add a space after it.

Here:

\begin{itemize}
\tightlist
\item
  \texttt{-i} and \texttt{-I}: the R1 and R2 input files
\item
  \texttt{-o} and \texttt{-O}: where to write the trimmed R1 and R2
  files
\item
  \texttt{-\/-thread\ 2}: let fastp use 2 CPUs, the same number that we
  requested from SLURM with \texttt{-\/-cpus-per-task=2}
\end{itemize}

When fastp is done, it prints a summary to the screen. It shows, for
example, how many reads there were before and after filtering.

Now look at the output of the two \texttt{ls} commands. The trimmed
files are in \texttt{results/fastp}, as we asked. But fastp also made
two reports, \texttt{fastp.html} and \texttt{fastp.json}, and put them
in the folder we ran the command from. We never asked for these names
and fastp uses them by default. If we now ran fastp on the next sample,
it would write its reports under the same names, and overwrite the
reports of Sample-DUMMY1.

This is why it is worth running a tool on one sample first and looking
carefully at the help page. In the help page, we find the options
\texttt{-h} and \texttt{-j} to choose the names of the two reports
ourselves. We use them in the loop below. The reports in the current
folder are not needed anymore, so we remove them:

\begin{Shaded}
\begin{Highlighting}[]
\CommentTok{\# Remove the two reports with the default names}
\FunctionTok{rm}\NormalTok{ fastp.html fastp.json}

\CommentTok{\# Check that they are gone}
\FunctionTok{ls} \AttributeTok{{-}l}
\end{Highlighting}
\end{Shaded}

\subsection{Step 2: Make a list of
samples}\label{step-2-make-a-list-of-samples}

Our loop will repeat fastp once per sample, so we need a list with the 4
sample names. We build this list from the file names with \texttt{cut},
step by step:

\begin{Shaded}
\begin{Highlighting}[]
\CommentTok{\# List the R1 files only. Each sample has exactly one R1 file, so each sample is listed once}
\FunctionTok{ls}\NormalTok{ data/seq\_project/}\PreprocessorTok{*}\NormalTok{/}\PreprocessorTok{*}\NormalTok{\_R1.fastq.gz}

\CommentTok{\# Keep only the file name: the 4th field when we split the path at each /}
\FunctionTok{ls}\NormalTok{ data/seq\_project/}\PreprocessorTok{*}\NormalTok{/}\PreprocessorTok{*}\NormalTok{\_R1.fastq.gz }\KeywordTok{|} \FunctionTok{cut} \AttributeTok{{-}f4} \AttributeTok{{-}d} \StringTok{"/"}

\CommentTok{\# Keep only the sample name: the 1st field when we split the file name at each \_}
\FunctionTok{ls}\NormalTok{ data/seq\_project/}\PreprocessorTok{*}\NormalTok{/}\PreprocessorTok{*}\NormalTok{\_R1.fastq.gz }\KeywordTok{|} \FunctionTok{cut} \AttributeTok{{-}f4} \AttributeTok{{-}d} \StringTok{"/"} \KeywordTok{|} \FunctionTok{cut} \AttributeTok{{-}f1} \AttributeTok{{-}d} \StringTok{"\_"}
\end{Highlighting}
\end{Shaded}

The last command prints exactly the list we want, so we store it in a

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{ls}\NormalTok{ data/seq\_project/}\PreprocessorTok{*}\NormalTok{/}\PreprocessorTok{*}\NormalTok{\_R1.fastq.gz }\KeywordTok{|} \FunctionTok{cut} \AttributeTok{{-}f4} \AttributeTok{{-}d} \StringTok{"/"} \KeywordTok{|} \FunctionTok{cut} \AttributeTok{{-}f1} \AttributeTok{{-}d} \StringTok{"\_"} \OperatorTok{\textgreater{}}\NormalTok{ samples.txt}

\CommentTok{\# Check the list: we expect 4 sample names}
\FunctionTok{cat}\NormalTok{ samples.txt}
\FunctionTok{wc} \AttributeTok{{-}l}\NormalTok{ samples.txt}
\end{Highlighting}
\end{Shaded}

A list file like \texttt{samples.txt} has a few advantages. You can open

\end{tcolorbox}

\subsection{\texorpdfstring{Step 3: Build the loop with
\texttt{echo}}{Step 3: Build the loop with echo}}\label{step-3-build-the-loop-with-echo}

Like on day 1, we start with a loop that only prints what it works on:

\begin{Shaded}
\begin{Highlighting}[]
\ControlFlowTok{for}\NormalTok{ sample }\KeywordTok{in} \VariableTok{$(}\FunctionTok{cat}\NormalTok{ samples.txt}\VariableTok{)}\KeywordTok{;} \ControlFlowTok{do}
    \BuiltInTok{echo} \VariableTok{$sample}
\ControlFlowTok{done}
\end{Highlighting}
\end{Shaded}

This should print the 4 sample names. One part is new here:
\texttt{\$(cat\ samples.txt)}. \texttt{cat\ samples.txt} prints the
content of the file. The \texttt{\$(\ )} around it takes this printed
text and puts it into the command, at the place where it stands. This is
called \textbf{command substitution}. So for bash, the first line
becomes
\texttt{for\ sample\ in\ Sample-DUMMY1\ Sample-DUMMY2\ Sample-DUMMY3\ Sample-DUMMY4;\ do}.

Important: Bash splits the text from \texttt{samples.txt} at every new
line, but also at every space. So each line in the list file must
contain one name, without spaces.

Next, we check that we find the right input files for each sample. We
use \texttt{ls} instead of \texttt{echo}, because \texttt{ls} shows us
which files the wildcard actually matches:

\begin{Shaded}
\begin{Highlighting}[]
\ControlFlowTok{for}\NormalTok{ sample }\KeywordTok{in} \VariableTok{$(}\FunctionTok{cat}\NormalTok{ samples.txt}\VariableTok{)}\KeywordTok{;} \ControlFlowTok{do}
    \BuiltInTok{echo} \StringTok{"Sample: }\VariableTok{$sample}\StringTok{"}
    \FunctionTok{ls}\NormalTok{ data/seq\_project/}\PreprocessorTok{*}\NormalTok{/}\VariableTok{$\{sample\}}\NormalTok{\_R1.fastq.gz}
    \FunctionTok{ls}\NormalTok{ data/seq\_project/}\PreprocessorTok{*}\NormalTok{/}\VariableTok{$\{sample\}}\NormalTok{\_R2.fastq.gz}
\ControlFlowTok{done}
\end{Highlighting}
\end{Shaded}

Each \texttt{ls} should print exactly \textbf{one} file. This is the
moment to check what your wildcard matches. Imagine you had sequenced
Sample-DUMMY1 twice, and had two folders with a
\texttt{Sample-DUMMY1\_R1.fastq.gz} file. Then the wildcard would match
both files, and fastp would get the wrong input. Always look at what a
wildcard matches before you give it to a tool.

Notice that we write \texttt{\$\{sample\}}, with curly brackets, and not
\texttt{\$sample}. The curly brackets show bash where the variable name
ends. Without them, bash reads \texttt{\$sample\_R1} as a variable
called \texttt{sample\_R1}. That variable doesn't exist, so bash quietly
replaces it with nothing, and the path becomes
\texttt{data/seq\_project/*/.fastq.gz}. Bash does not give an error for
this. Use the curly brackets whenever text follows directly after a
variable name.

\subsection{Step 4: A dry run of the full
command}\label{step-4-a-dry-run-of-the-full-command}

Now we put the whole fastp command into the loop, but with \texttt{echo}
in front of it. Bash then prints each command instead of running it. We
add \texttt{-h} and \texttt{-j} to give each sample its own reports:

\begin{Shaded}
\begin{Highlighting}[]
\ControlFlowTok{for}\NormalTok{ sample }\KeywordTok{in} \VariableTok{$(}\FunctionTok{cat}\NormalTok{ samples.txt}\VariableTok{)}\KeywordTok{;} \ControlFlowTok{do}
    \BuiltInTok{echo} \StringTok{""} 
    \BuiltInTok{echo}\NormalTok{ fastp }\DataTypeTok{\textbackslash{}}
        \AttributeTok{{-}i}\NormalTok{ data/seq\_project/}\PreprocessorTok{*}\NormalTok{/}\VariableTok{$\{sample\}}\NormalTok{\_R1.fastq.gz }\DataTypeTok{\textbackslash{}}
        \AttributeTok{{-}I}\NormalTok{ data/seq\_project/}\PreprocessorTok{*}\NormalTok{/}\VariableTok{$\{sample\}}\NormalTok{\_R2.fastq.gz }\DataTypeTok{\textbackslash{}}
        \AttributeTok{{-}o}\NormalTok{ results/fastp/}\VariableTok{$\{sample\}}\NormalTok{\_R1.trimmed.fastq.gz }\DataTypeTok{\textbackslash{}}
        \AttributeTok{{-}O}\NormalTok{ results/fastp/}\VariableTok{$\{sample\}}\NormalTok{\_R2.trimmed.fastq.gz }\DataTypeTok{\textbackslash{}}
        \AttributeTok{{-}h}\NormalTok{ results/fastp/}\VariableTok{$\{sample\}}\NormalTok{.html }\DataTypeTok{\textbackslash{}}
        \AttributeTok{{-}j}\NormalTok{ results/fastp/}\VariableTok{$\{sample\}}\NormalTok{.json }\DataTypeTok{\textbackslash{}}
        \AttributeTok{{-}{-}thread}\NormalTok{ 2}
\ControlFlowTok{done}
\end{Highlighting}
\end{Shaded}

This prints 4 fastp commands, one per sample. Read them carefully: do
the R1 and R2 input files belong to the same sample? Does every sample
get its own output names? If something looks wrong, it is much easier to
fix it now than after the job has run.

\begin{tcolorbox}[enhanced jigsaw, colbacktitle=quarto-callout-important-color!10!white, rightrule=.15mm, bottomrule=.15mm, opacitybacktitle=0.6, toptitle=1mm, colframe=quarto-callout-important-color-frame, arc=.35mm, toprule=.15mm, titlerule=0mm, title=\textcolor{quarto-callout-important-color}{\faExclamation}\hspace{0.5em}{Important: Don't put quotes around a path with a wildcard}, bottomtitle=1mm, breakable, colback=white, left=2mm, leftrule=.75mm, opacityback=0, coltitle=black]

In scripts that you find online, or that an AI tool writes for you,
variables are often written in quotes, for example \texttt{"\$sample"}.
That is a good habit in general. But be careful with wildcards. Inside
quotes, bash does not replace the \texttt{*} with the matching file
names. With
\texttt{-i\ "data/seq\_project/*/\$\{sample\}\_R1.fastq.gz"}, fastp
would look for a folder that is literally called \texttt{*}, and stop
with an error.

That is why we write the input paths without quotes, directly in the
fastp command. Our names contain no spaces, so this is safe here.

The \texttt{scp} command in the exercise below, where we copy the fastp
reports to our own computer, is the opposite case. There, we put quotes
around the wildcard on purpose: the quotes stop your own computer from
using the wildcard, so that Crunchomics can use it to find the files.

\end{tcolorbox}

Both tables have many columns, which makes them hard to compare by eye.
On day 1, we used \texttt{cut} to select columns. Here, we use
\textbf{awk}, a small programming language for working with tables in
text files. awk reads a file line by line, splits each line into
columns, and lets us choose what to do with each line.

Let's print the file name, the number of reads and the average read
length (columns 1, 4 and 7) of both tables:

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{awk} \AttributeTok{{-}F}\StringTok{\textquotesingle{}\textbackslash{}t\textquotesingle{}} \StringTok{\textquotesingle{}FNR \textgreater{} 1 \{print $1, $4, $7\}\textquotesingle{}}\NormalTok{ results/seqkit/stats\_raw.txt results/seqkit/stats\_trimmed.txt}
\end{Highlighting}
\end{Shaded}

Here:

\begin{itemize}
\tightlist
\item
  \texttt{-F\textquotesingle{}\textbackslash{}t\textquotesingle{}}: the
  columns are separated by tabs (\texttt{\textbackslash{}t} stands for a
  tab)
\item
  \texttt{\textquotesingle{}...\textquotesingle{}}: the awk program, in
  single quotes so that bash does not change anything in it
\item
  \texttt{FNR\ \textgreater{}\ 1}: only work on lines with a line number
  above 1. This skips the header line. \texttt{FNR} is the line number
  within the current file, so the header is skipped in both files
\item
  \texttt{\{print\ \$1,\ \$4,\ \$7\}}: print columns 1, 4 and 7. In awk,
  \texttt{\$4} means ``column 4''. This is not the same as a bash
  variable
\item
  We give awk two files, and it works through them one after the other
\end{itemize}

This prints 16 lines: first the 8 raw files, then the 8 trimmed files.
Compare the number of reads and the average length of Sample-DUMMY1
before and after trimming.

For those who want to learn more bash: we can also write this loop
without \texttt{samples.txt}. We then loop directly over the R1 files,
and let bash work out the matching R2 file and the sample name:

\begin{Shaded}
\begin{Highlighting}[]
\ControlFlowTok{for}\NormalTok{ R1 }\KeywordTok{in}\NormalTok{ data/seq\_project/}\PreprocessorTok{*}\NormalTok{/}\PreprocessorTok{*}\NormalTok{\_R1.fastq.gz}\KeywordTok{;} \ControlFlowTok{do}
    \VariableTok{R2}\OperatorTok{=}\VariableTok{$\{R1}\OperatorTok{/}\SpecialStringTok{\_R1}\OperatorTok{/}\NormalTok{\_R2}\VariableTok{\}}
    \VariableTok{sample}\OperatorTok{=}\VariableTok{$(}\FunctionTok{basename} \VariableTok{$R1}\NormalTok{ \_R1.fastq.gz}\VariableTok{)}
    \BuiltInTok{echo} \StringTok{"Sample: }\VariableTok{$sample}\StringTok{, R1: }\VariableTok{$R1}\StringTok{, R2: }\VariableTok{$R2}\StringTok{"}
\ControlFlowTok{done}
\end{Highlighting}
\end{Shaded}

\begin{itemize}
\tightlist
\item
  \texttt{\$\{R1/\_R1/\_R2\}}: takes the value of \texttt{R1} and
  replaces the first \texttt{\_R1} with \texttt{\_R2}. This turns the
  path to the R1 file into the path to the R2 file
\item
  \texttt{basename\ \$R1\ \_R1.fastq.gz}: \texttt{basename} removes the
  folders from a path and keeps only the file name. If you give it an
  ending as second argument, it removes that ending too. What is left is
  the sample name
\item
  \texttt{\$(\ )}: the command substitution from above stores the output
  of \texttt{basename} in the variable \texttt{sample}
\end{itemize}

This is shorter, but you need to know the extra syntax to read it. A
list file is easier to check, and easier to change if you want to run
only some samples.

If your list file has several columns, for example a sample name and a
group, a \texttt{while} loop can read both columns into separate
variables. The
\href{https://scienceparkstudygroup.github.io/ibed-bioinformatics-page/source/core_tools/bash-for-loops.html}{IBED
for-loops page} explains this, and builds a loop step by step with
another example.

\end{tcolorbox}

\section{Going further}\label{going-further}

\begin{tcolorbox}[enhanced jigsaw, colbacktitle=quarto-callout-tip-color!10!white, rightrule=.15mm, bottomrule=.15mm, opacitybacktitle=0.6, toptitle=1mm, colframe=quarto-callout-tip-color-frame, arc=.35mm, toprule=.15mm, titlerule=0mm, title=\textcolor{quarto-callout-tip-color}{\faLightbulb}\hspace{0.5em}{Tip: Running many files in parallel with job arrays (optional)}, bottomtitle=1mm, breakable, colback=white, left=2mm, leftrule=.75mm, opacityback=0, coltitle=black]

Our fastp loop runs inside a single job, so the samples are processed
one after another. With 4 small samples, that is fine. With hundreds of
samples, it can take a long time, while the HPC has enough space to run
several of them at the same time.

For this section, we go back to \texttt{seqkit\ stats} and run it on
each file separately, one job per file. How would we run such jobs
efficiently?

We can use a \textbf{job array}, which allows us to:

\begin{itemize}
\tightlist
\item
  Run several jobs with the same settings: the same CPUs, memory and
  software
\item
  Run these jobs in parallel (at the same time), instead of one after
  the other
\end{itemize}

Let's start with making a list of the files we want to work with, using
what we learned on day 1:

Next, we use this text file in our job array. Store the following in
\texttt{scripts/array.sh}:

\begin{Shaded}
\begin{Highlighting}[]
\CommentTok{\#!/bin/bash}
\CommentTok{\#SBATCH {-}{-}job{-}name=my\_array}
\CommentTok{\#SBATCH {-}{-}output=logs/array\_\%A\_\%a.out}
\CommentTok{\#SBATCH {-}{-}error=logs/array\_\%A\_\%a.err}
\CommentTok{\#SBATCH {-}{-}array=1{-}8}
\CommentTok{\#SBATCH {-}{-}cpus{-}per{-}task=1}
\CommentTok{\#SBATCH {-}{-}mem=5G}

\CommentTok{\# The number of the current job in the array (1 to 8 for our 8 files)}
\VariableTok{index}\OperatorTok{=}\VariableTok{$SLURM\_ARRAY\_TASK\_ID}

\CommentTok{\# Read the file name on line number $index of fastq\_files.txt}
\VariableTok{current\_sample}\OperatorTok{=}\VariableTok{$(}\FunctionTok{sed} \AttributeTok{{-}n} \StringTok{"}\VariableTok{$\{index\}}\StringTok{p"}\NormalTok{ fastq\_files.txt}\VariableTok{)}

\CommentTok{\# Print what is happening}
\BuiltInTok{echo} \StringTok{"Now Job}\VariableTok{$\{index\}}\StringTok{ runs on }\VariableTok{$\{current\_sample\}}\StringTok{"}

\CommentTok{\# Run the actual job}
\ExtensionTok{seqkit}\NormalTok{ stats }\AttributeTok{{-}b} \AttributeTok{{-}a} \AttributeTok{{-}T} \AttributeTok{{-}o}\NormalTok{ results/seqkit/}\VariableTok{$\{current\_sample\}}\NormalTok{\_stats.txt data/seq\_project/}\PreprocessorTok{*}\NormalTok{/}\VariableTok{$\{current\_sample\}} \AttributeTok{{-}{-}threads}\NormalTok{ 1}
\end{Highlighting}
\end{Shaded}

In the script, we use some new SLURM options:

\begin{itemize}
\tightlist
\item
  \texttt{\#SBATCH\ -\/-array=1-8}: sets up a job array with 8 jobs,
  numbered 1 to 8. We choose 1-8 because we have exactly 8 fastq.gz
  files
\item
  \texttt{\#SBATCH\ -\/-output=logs/array\_\%A\_\%a.out}: \texttt{\%A}
  is replaced by the job ID that SLURM assigns, and \texttt{\%a} by the
  number of the job in the array
\item
  \textbf{Important}: do the individual jobs in your array use a lot of
  CPUs or memory? Then you might not want to run all of them at the same
  time. With \texttt{\#SBATCH\ -\/-array=1-8\%2}, SLURM runs at most 2
  jobs at the same time, and starts the next ones when these have
  finished. Try to use no more than \textasciitilde20\% of the
  Crunchomics cluster at the same time.
\end{itemize}

The script does the following:

\begin{itemize}
\tightlist
\item
  \texttt{index} stores the value of \texttt{SLURM\_ARRAY\_TASK\_ID},
  the number of the current job within the array. This is 1 for the
  first job, 2 for the second, \ldots, and 8 for the last one
\item
  \texttt{sed\ -n\ "\$\{index\}p"\ fastq\_files.txt} prints one line of
  \texttt{fastq\_files.txt}: line 1 for job 1, line 2 for job 2, and so
  on. We store this file name in the variable \texttt{current\_sample}.
  For the first job, this is \texttt{Sample-DUMMY1\_R1.fastq.gz}
\item
  \texttt{echo} records which job works on which file
\item
  Finally, we run \texttt{seqkit\ stats} on the file stored in
  \texttt{current\_sample}. Each job writes its own table, named after
  its input file, so the 8 jobs don't overwrite each other's output
\end{itemize}

Submit the script with \texttt{sbatch\ scripts/array.sh}. If we check
what is happening right after submitting the job with \texttt{squeue},
we should see something like this:

We see that jobs 1-4 are already running, and jobs 5-8 are waiting for
space. That is one of the useful things about a job manager such as
